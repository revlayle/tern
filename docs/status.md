- **M13 follow-up** (2026-11-07; settled 2026-11-03/04).
  - *`volatile` over an overlay (spec 8.5).* A `volatile` fixed-address variable may overlap an overlay's file; without it the error suggests `volatile` or the overlay's own name. Overlap with the resident program is still an error. A write to a fixed variable that lies in an overlay area (`VariableSymbol.InOverlayArea`, set in the checker) makes the optimizer forget every variable (`Optimizer.ForgetWrite`), like a write through a pointer, whatever other volatile ranges it is in. Overlap is now checked against each section of the overlay, not its whole span.
  - *Fixed data in an overlay module (question 58).* `SectionStart` of such data carries the module; the assembler lays the module's other sections around it (first fit in the area, `Assembler`), gaps zero-filled, and the file starts at the area's start. Fixed data of two overlays may share an address. Errors (`CheckFixedData`): outside the module's own area; a resident module's or the main file's fixed data in an overlay area; overlap with the module's other fixed data (assembler) or fixed variables (`CheckFixedAddresses`). Unused data is dropped, so the checks apply only to data that is used.
  - *Sibling uses (question 56).* `addr()` of a function of another overlay in the same area is an error (`TakeFunctionAddress`); using fixed data of a sibling too. Resident code and overlays in other areas may still take these addresses.

- **M12, memory layout and binaries without `main`** (2026-11-03).
  - **Syntax.** `memory { first..=last kind [name] }` right after the imports (`program`, `zeropage`, `reserved`, `region name`, `volatile`; `overlay name` parses and gives "'overlay' is not supported yet"). Kinds are words only inside the block (`volatile` is a keyword anyway, so the parser accepts both). `export a, b` is a top-level declaration; `export` is reserved. `@ name` after a `var`/`data` is a region when the name is one of the block's regions and nothing else is declared with that name; otherwise an address expression. `data x: T @ addr = ...` and `@ region` work; `@ zp` on data is an error.
  - **`MemoryLayout`** (`Semantics/MemoryLayout.cs`): evaluated by the checker once the main file's constants are declared, so ranges can use constants from imports and constants declared below the block. `program`/`zeropage` lines replace the platform's areas; `reserved`, `region` and `overlay` ranges are taken out of the platform's program areas and free zero page when the block does not replace them. Errors: backwards or out-of-memory range, `zeropage` above `$FF`, overlapping ranges (except `volatile`), a region declared twice, no program area left, a `main` program whose first area does not start at `$0801`, a block in a module. `volatile` ranges make fixed-address variables in them volatile (applied after all globals are declared).
  - **Placement** (`Backend/Assembler.cs`): the code generator emits sections (`SectionStart`: the startup code, each function, each initialized global, each fixed data item) and one `Reserve` for the variables. The assembler fills the program areas first fit in order, and a section never crosses an area boundary; data at a fixed address punches a hole the code goes around. The variables go in the first area with room after its code (`RamPlan` offsets from the block's start, as before). A section that does not fit gives an error listing each area with its use and what is in it. `Assembler.Assemble` returns segments; `TernCompiler` writes the file from the lowest to the highest segment, gaps zero-filled; the report says so and lists the areas and regions. Added to `CompileResult`: `Sections`, `Areas`, `Entries`, `ApiModule`, `ApiModuleName`.
  - **Regions** (`Allocator`): variables and data with `@ region` are placed in declaration order at the region's start: zeroed variables first (cleared at startup by one block per region), then `noinit` ones, then data (part of the program file, at that address). A full region is an error. A `var @ region` with an initial value is an error (only data can be initialized there). `@ region` works in the main file only (a module is checked before the block exists).
  - **Zero page** is a list of ranges (flattened in address order). A variable must lie in consecutive bytes: one that would straddle a gap is an error naming the ranges.
  - **Fixed addresses**: data with `@ address` must lie in a program or reserved area; a fixed `var` still may not overlap what the compiler placed (now computed per area), and may not overlap fixed data. The existing messages are unchanged.
  - **Binaries** (`export`): the checker validates the exports (plain functions of the main file, register parameters only, no `setup`, no duplicates, no interrupt/inline/fixed-address functions, no `main` next to them) and gives them one synthetic root (`(entries)`), so their frames and private variables share memory. `TernCompiler` writes the jump table (`jmp setup`, then the exports in order), then `setup` (the startup code, `rts`), then the functions; no BASIC line; `Entry` is the table. `Backend/RegisterUse.cs` works out which of A, X, Y a function changes, through everything it calls (a `jsr`/`jmp` it cannot name counts as changing all three, a routine at a fixed address as changing what it does not keep); `Backend/BinaryInterface.cs` writes `name_api.tern`: `CODE_FIRST/LAST` (the file), `VARS_*` (variables outside the file), `<REGION>_*` (regions outside the file), `ZP_*` (zero page the binary uses), then `fn setup() @ $C000 keeps ...` and one routine per export with `keeps` = not changed and not a return register. ## Known limitations and technical debt

Not bugs; things to improve, mostly in M7 (optimizer).

- Register parameters in A, register pairs, and X/Y parameters of bodies that need the register are stored on entry and reloaded where A was changed.
- After the step of a memory loop counter, the counter is reloaded with `lda` right after it was stored.
- A `for` bound that is a global variable is copied to a temporary (only locals and parameters are used directly, since calls could change a global).
- Only innermost loops get a register automatically, and only when no other register is held (a kept parameter or an outer `using` loop), so nested loops keep the outer counter in memory.
- The optimizer forgets everything at labels reached from a jump table or by address and at every `jsr` or `brk` (an asm instruction only forgets what it changes); it does not track values across calls to functions it could see into.
- The register analysis tracks only equality with immediates and memory bytes; it does not fold constants (`lda #3` / `clc` / `adc #1` stays).
- Evaluation order: in `a + b` where `b` needs a temporary, `b` is evaluated before `a`. Matters only if both call functions with side effects.
- Only one zero-page range per platform is used (C64: `$02-$8F`; `$FB-$FE` is unused unless a variable is placed there with `@`).
- When the value of `p[i] = v` changes Y (it reads through a pointer with another index, or calls a function), A is still saved to a temporary while Y is loaded.
- `addr()` cannot be used in global or data initializers: addresses are known only at link time. Tables of pointers to data must be filled at runtime.
- `VariableSymbol.AddressTaken` is set by `addr()` and by `#name.lo`/`#name.hi` in assembly. The M7 optimizer must not cache such variables in registers across pointer writes or asm blocks.
- `AsmEffects` are unions over the whole block (a register "read" may be one the block set itself first, as in `clc` / `adc`). Good enough for the current checks; the optimizer may want "read before written".
- Inside a `for ... using X` loop, only routines that declare `keeps X` may be called. An `asm fn` that never touches X is still rejected; `AsmEffects` would make allowing it easy (spec 6.1: the compiler may use each function's actual register use).
- `mem.fill` reloads `value` on every byte (`lda value` / `sta (dst),y`): 13 cycles per byte instead of 11. Loop-invariant loads are for the optimizer.
- A `for` bound such as `count.hi` is used in place only when `count` is a local or parameter the body does not change; a global's byte is copied to a temporary before the loop.
- Evaluation order (spec 5, review M18 suggestion 6, pre-existing): in a 16-bit assignment to an element with a simple index (`k[vi] = k[j] + w`), the index is loaded after the value is computed, although spec 5 says the index is evaluated first. Observable only with a volatile index or value.
- Layout changes move arrays and routines across page boundaries: M18 part 1 made `interp` 22 cycles slower that way (its `code` table now crosses a page) and `math.mul16`'s `beq` cross a page. F12 (part 3) places arrays; branches inside routines are not placed.
- Import cycles: declarations are processed module by module, so in a cycle (a imports b, b imports a) a constant of the later module cannot be used in a declaration of the earlier one. The error says so and suggests moving the constant. Function bodies are not affected.
- A pointer that is a field of a struct variable (`player.next.hp`) is always copied to a zero-page temporary, even when the struct is in zero page and could be used as `(player+3),y` directly.
- A field used as a `for` bound (`for i in 0..s.count`) is copied to a temporary, like any bound that is not a plain local or parameter.
- Structs are not put in zero page by usage (step 3 of 8.2), only with `@ zp`, like arrays.
- Struct field offsets use a constant expression; a constant declared later in the same file than the struct cannot be used, since structs are laid out right after the file's constants. Globals cannot be used at all (an offset must be a constant anyway).
- A struct with `@` gaps in an array of structs costs one table (n bytes) per gap byte.
- A `match` jump table always checks the bounds (`cmp #span` / `bcs`), even when the value cannot be out of range (e.g. `band` in the raster example, which is always 0-7).
- A `match` on a value already in a register (a `using X` loop variable) copies it to A first (`txa`).
- An inline function's parameters go through its frame in memory, as for a call; register parameters are stored and reloaded.
- Calling an inline function counts as a call: it is not allowed inside a `for ... using X` loop. (Sharing one with no memory between main and a handler is allowed since M7.)
- An interrupt handler saves every register that any of its instructions changes, on every path.
- A function that is both called as a part and installed as a handler is an error: it is compiled in one form only (question 45).
- The multiplexer's raster code costs about 220 cycles per interrupt plus 110 per sprite (9 interrupts a frame with 24 sprites): grouping more sprites per interrupt, or skipping the multicolor and expand-x updates when no sprite uses them, would save about 1,000 cycles a frame. `update()` costs 233 cycles per sprite.
- The scroller copies 14 cycles a byte; an unrolled version with absolute addressing for each direction would take about 10.
- The color redraw (`COLORS = true`) is untested against the beam (the stand-in VIC does not read color RAM). It can fall behind the beam in the lower rows when combined with the multiplexer's interrupts (review finding 4); the scroll header says so.
- `src/lib/wide.tern` has the 24- and 32-bit code written out twice (generated once from a template).

## Questions for the spec session

65. **Reads of a fixed address outside the volatile areas (spec 4).** Spec 4 makes only the platform's volatile areas, `volatile` variables and two-root globals volatile, so `var reg: u8 @ $C000` is ordinary memory whose reads may be removed. `MatchTests.A_match_with_only_a_default_still_reads_a_volatile_value` (M6 review) expects the read of such a variable to stay. Provisional: M18's dead-load removal never removes a load from a fixed address (hardware the platform table does not list, such as a cartridge register); the older redundant-load removal (M7) already removes a re-read of one when a register holds its value. Should a fixed address outside the volatile areas be ordinary memory, as spec 4 says, or should every read of a fixed address happen?

66. **Spec 11 rows after M18 part 1** (review M18, suggestion 3). `-x` (u8) is now `lda #0 / sec / sbc x` (5 bytes, 7 cycles), shorter than the row's `lda x / eor #$FF / clc / adc #1`; the row could state the real code. Also: `x = 0` (and any store of 0) at the start of `main`, before any label, branch, call or asm, into a global the startup cleared and main has not written, now generates no code (`RemoveStoresOfStartupZeros`), so the cost of `x = 0` depends on where it is; the spec may want to say so next to the `x = 0` row or in 8.
