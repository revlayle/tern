- **Marked failures.** In a temporary worktree the `Skip` was removed from the nine theories (`Fails_*`, `Open_question_170`). 80 cases ran and all 80 failed. This matches the status table: 21 + 2 + 30 + 6 + 1 + 12 + 2 + 2 + 4 = 80. So each one gives R2 a target that fails today.
- **Classification.** Each group was checked against its finding. Backend 3 includes the 8-bit `port <<= 2` from its own evidence. R1-1 (`lda x / bne / dec x+1 / dec x` reads the low byte twice) breaks spec 4 whatever question 170 decides. Question 170 is written up in the status file with a proposal.
- **Matrix error cases.** Each one was compiled with its message logged (152 cases). Every message matches the reason `ExpectedError` gives: a call in a `using` loop, Y for a pointer, the left side of an assignment, the constant step, the shift overflow, the range that never runs. Four "write to a call" cases in a `using` loop report the loop's call error first, which is right.
- **The optimizer switch.** `Optimizer.Run` has exactly two callers (`CodeGen.cs:72` and `:440`), and both are behind `_optimize`. The default is `true`, and the CLI does not expose it. No benchmark or `SkillTests` output moved.
- **The random start's adjustments** (`669124d`). All seven changed tests set memory that the program reads but nothing writes: fixed-address variables, stand-in buffers, colour RAM, bytes past a load. None hides a compiler result.
- **Volatile counts.** The listing counts of volatile reads are gone (`VolatileTests`, `IndexReads`). What remains in `MatchTests` and `SmallShapeTests` are exact shape strings, not counts.
- **`BusLog.Writes`.** It leaves out an NMOS write-back only when that write comes on the bus access right after a read of the same value and is followed at once by another write. Only a read-modify-write instruction does that, because a program's own `lda`/`sta` have opcode fetches between them.

## Findings

### 1. Six emulator harnesses still start at zero (must fix)

- Where:
  - `BinaryTests.cs:36-41`: `Binary`, used by 15 tests, a new `Ram` and `new Cpu6502(Ram) { SP = 0xFF }`.
  - `BinaryTests.cs:374-378`: `Emulate`.
  - `SpriteTests.cs:65-70`: `Rig`, 7 uses, about 23 cases.
  - `LibraryTests.cs:610-615`: the raster example.
  - `AtariLibraryTests.cs:223, 236`: the VBI test's local `Run`.
  - `AtariLibraryTests.cs:287-289`: `Wait_frame_returns_when_the_frame_counter_changes`.
- What: each of these builds its own `Ram` and `Cpu6502` and never calls `StartState.Fill` or `StartState.Set`. About 50 end-to-end tests of compiled Tern programs therefore still run on zero memory and zero A, X and Y. Exported binary entries, sprite and raster interrupt code, and the Atari VBI path are where a register that is never loaded, or a variable the startup code does not clear, would hide. Finding 2 of the tests review gives exactly that reason. The roadmap's "done when" says "the random start ... on for the whole suite". The status file says "used by `Run` and `Library`", which is accurate but is less than the roadmap item.
- Fix: in each harness, call `StartState.Fill(ram)` before `ram.Load` and `StartState.Set(cpu)` after creating the CPU. For `Binary.Call`, the registers it sets are the entry's arguments, so leave that as it is. Fix any test that then fails, the same way as in `669124d`, and list any compiler bug it shows as a marked failure. `ComparisonTests` measures other compilers' output and can stay as it is. Say so in the status file.

### 3. The matrix's error cases accept any compile error (suggestion)

- Where: `OperandMatrixTests.cs:245`.
- What: `Assert.Throws<CompileError>` passes for any error. Today every message is the intended one (see "What was checked"). But a regression that gives another error would still pass, such as a wrong type error in place of "p[i] needs the Y register" in a `using Y` loop. The matrix is meant to test the checker's tree walks too, so the reason matters.
- Fix: have `ExpectedError` return a fragment of the message (for example "can change X", "needs the Y register", "left side of an assignment", "between -127 and 127", "does not fit in u8", "never runs") and assert that the message contains it. A case where two rules apply should expect the one the checker reports first.

### 4. The matrix uses 8-bit operands only (suggestion)

- Where: `OperandMatrixTests.cs:34-47` and `Source`.
- What: every form is a `u8`. The 16-bit paths (`Gen16`, element stores of two bytes) are where backend 3 and backend 5 sit. Backend 5 was found only by the separate hand-written theory under the matrix. `VolatileAccessTests` covers 16-bit targets for volatile memory only. The roadmap item asks for operands varied "for the operators and statements", and the review's finding 1 lists no width. So this is not a "done when" gap, but it is the cheapest way to widen what the matrix finds.
- Fix: a `u16` column for the places that make sense at 16 bits: the operators, the compares, the assignments, the index write with a `u16` element, the pointer store into `ptr u16`, and return. It could also be added in R2, next to the fixes it would guard.

### 5. `LibraryTests.WatchBus` duplicates `BusLog` (suggestion)

- Where: `LibraryTests.cs:433-442`, used once, by the raster example.
- What: a second bus wrapper that logs the writes of one address. It is the kind of copy that finding 7 removes, and it does not leave out the NMOS write-back.
- Fix: use `BusLog` there. This fits in with finding 1, since that test's harness is touched anyway.

### Note: `tern run` starts at zero

The tool tests that go through `Runner.Run` (22 calls) start with zero memory, because that is the `tern run` machine model. This is outside R1: those tests check the tool, not a test harness. Whether `tern run` itself should start with filled memory, as a real machine does, is a question for R3 (tools) or the spec session.
