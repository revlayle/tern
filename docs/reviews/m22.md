# Review: M22, `const fn` and code generators, branch `m22-const-fn`

## First review (`23633c8`), 2026-11-11

**Not ready to merge: one must-fix item.** Two generator calls in one asm block fail when the generators use local `.labels` or `label()`, because every call starts its label numbering at 1. Everything else works as specified: the interpreter's results match C# for every case I tried, arrays behave as values, errors and the step limit read as the spec says, and generated code is listed under its `emit` line with the call.

36 CPU tests and 2742 compiler tests pass. No benchmark changed (1254 / 350780); `SkillTests` pass.

Checked by hand (programs compiled with the branch's `tern`, run with `tern run`):

- `for` lists: `9..=0`, `0..10 step 3`, `10..0 step -3`, `-3..=3` into `i8`, `round` / `floor` / `ceil` / `trunc` of halves and negatives, a `var` global from a list. All bytes as expected.
- Arrays are values: `var r = g[0]; r[0] = 9` leaves `g` unchanged, and `b = a; b[0] = 7` leaves `a` unchanged.
- A const fn that reads `data` declared after the constant that calls it works. Cycles through a constant, through `len(t)` in `t`'s own list, and through a const fn reading the table it fills are each "'X' depends on itself".
- `while true` in a const fn stops with the spec's step-limit message after about 1.2 s.
- A generator in a module (`gen.bump(3)`, emitting `inc cnt` on the module's private variable) called from main's asm: it runs, and the listing shows `gen.tern:4: emit { inc cnt }   (generated by line 5)` under the call line.
- The same generator, with a local label, called from two different `asm fn`s: works.

### Findings

**1. Must fix: two generator calls in one asm block give "Label ... is defined twice in this block".** `Interpreter.Generate` (`CompileTime/Interpreter.cs`) makes a new interpreter for each call line, and `_emits` (line 673) and `_labels` (line 31) start at 0 in each one. So the first `emit` of every call renames `.skip` to `.skip#1`, and the first `label()` of every call is `.label#1`. `Checker.ExpandGenerators` (`Checker.Asm.cs:37`) puts all calls' lines into one block, and `CheckAsm` (line 16) rejects the duplicate. Spec 4.1 says "The local `.labels` of one `emit` are its own, so a loop emitting `.skip:` gets a fresh label each time". A block that calls a generator twice (two screen halves, two sprite clears) is a normal use.

```tern
var v: [u8; 4]
const fn dec_nz(i: int) {
    emit {
        lda v + i
        beq .skip
        dec v + i
    .skip:
    }
}
fn main() {
    v[0] = 3
    asm {
        dec_nz(0)
        dec_nz(1)
    }
}
```

`error: Label '.skip#1' is defined twice in this block` (at the emit's `.skip:`). The same happens with `label()`: a `wait()` generator that does `var top = label()` / `emit { top: dex / bne top }`, called twice in one block, gives "Label '.label#1' is defined twice in this block". Two different generators that each have a local label also clash.

Fix: number the renamed labels per asm block (or per checker), not per interpreter. For example, `ExpandGenerators` can pass a counter that `Generate` continues from, so the second call's labels start where the first call's stopped. Tests: the same generator twice in one block, with a local label and with `label()`, run in the emulator; two different generators with the same local label name in one block.

**2. Suggestion: errors that come from the checker while a const fn runs do not get "(called from ...)".** `Interpreter.Error` adds the note, but errors the host throws do not pass through it: `ICompileTimeHost.Read` ("'score' is a variable, which a const fn cannot read"), `ConstFn` ("'g' runs on the 6502"), `SizeOf`, `Encode`, `DataArray` ("holds addresses", "holds structs"), and `Checker.ConstNegate` in `Unary` and `abs`. For example:

```tern
var score: u8 = 3
const fn f() -> int { return score }
const K = f()
```

gives `var.tern:2:30: error: 'score' is a variable, which a const fn cannot read. Use a const or data`, with no "(called from var.tern:3)". When the const fn is in a module, the error names only the module's line, not the main-file line that used it. Question 102 says that every error raised while a const fn runs gets the note, so the build does not match the question's description. Catch `CompileError` around the host calls (or in `CallConstFn`) and rethrow it through `Error` when `Top.Function` is set. The tests at `ConstFnTests.cs:483` and `:488` then need the note.

**3. Suggestion: the listing's "(generated by line N)" has no file name.** `CodeGen.cs:2557` writes `from.Line`. When the asm block that calls the generator is in a module, or the `emit` is in a different file than the call, the line number alone is ambiguous. In the module example above, `gen.tern:4: emit { inc cnt }   (generated by line 5)` means line 5 of `main.tern`. Use `Interpreter.Where(from)` when the call's file is not the main file, as the error notes already do ("generated by the call at main.tern:12").

**4. Suggestion: a few messages are hard to read.**
- An array argument's element: "The argument 't' of 'f''s element is a real, but an int is expected" (`Convert`, built from `$"{what}'s element"`). For example: "An element of the argument 't' of 'f' is a real, ...".
- A real that is a whole number prints without a decimal point: `const fn f() -> real { return 1 }` used in a table gives "This value is the real number 1, which a constant cannot hold". Printing it as `1.0` would show why it is a real (`CtReal.ToString`).
- A real that is NaN (`pow(-8, 1 / 3.0)`) gets "pow() gives a real too large for 64 bits" from `Finite`. "has no real value" (as for `sqrt`) would fit.
- Several new messages have no fix sentence: "Division by zero", "Only arrays can be indexed", "len() takes one array", "'+' needs numbers, not a bool", "'f' takes 1 argument(s), not 2", "This statement cannot run at compile time", "'x' is already declared at ...". "Division by zero" matches the checker's older message, so this is optional. "'f' takes 1 argument(s)" could say "1 argument" as `Builtin.Count` does.

**5. Suggestion: a mixed list of int arrays and real arrays is an error instead of a real array.** `MakeArray` promotes ints to reals for scalars, but for arrays it keeps the first element's type, so `[[1, 2], [1.5]]` gives "is a real, but an int is expected". Rare in practice; either promote nested element types too, or say in the message that the first element sets the type.

**6. Suggestion: a generator call inside an `emit` is reported only when the emit runs.** `Interpreter.Emit` reports "A generator is called as a statement of the const fn, not inside 'emit'" at run time. Spec 4.1 says an `emit` fragment is checked when the const fn is read. `ConstFnBodyCheck` could reject an `AsmGeneratorCall` in an `EmitStmt`'s lines.
