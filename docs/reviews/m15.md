## Findings

### 1. Suggestion: `arr[f()] = v` now reads `v` after calling `f`

`CodeGen.cs:730`. The new store path loads the index first, then the value. When the index calls a function that changes the value, the stored value differs from `main`:

```
var arr: [u8; 10]
var v: u8 = 1
fn h() -> u8 { v = 7; return 2 }
fn main() { arr[h()] = v }
```

`main` stores 1 (`lda v / sta _t0 / jsr h / tax / lda _t0 / sta arr,x`). The branch stores 7 (`jsr h / tax / lda v / sta arr,x`). The same happens with a `volatile` value, which is now read after the index call. This affects every plain array, not only record arrays. The spec does not define evaluation order, and pointer stores (`StorePointerByteIndexFirst`) already load the index first, so this is not a spec violation. But it is a change in behavior that question 60 does not mention. Either keep value-first when the index contains a call (`IndexIsCheap` is false and the index has a `CallExpr`), or ask the spec session to state the order. I'd add the side-effect case to question 60.

### 2. Suggestion: the offset table's name can collide with a user name

`Checker.Structs.cs:255`. The table is called `<name>_offsets`, which is a valid user name. With `indexed var list` and a user `var`, `data` or `fn` called `list_offsets`, the code is correct (references go by symbol, and an `asm` block's `list_offsets` is the user's), but:

- the listing has two `list_offsets:` labels;
- `Result.Symbols` and the `.vs` label file keep only one of them. With `fn list_offsets()`, the `.vs` has the function's address and not the table's. With `data list_offsets`, it has the table's address, and the user's data has no label in VICE.

Either report an error at the declaration ("'list_offsets' is the name of the offset table of 'list'"), or give the table a name a user cannot write.

### 3. Suggestion: unreachable error in `ParseIndexedVar`

`Parser.cs:346`. `IsIndexedWord` only matches when the next token is `var`, `linear` or `data`. `linear` and `data` are handled before this line, so the "'indexed' goes before 'var' ... found ..." branch can never run. Either delete it, or let `IsIndexedWord` match `indexed` followed by `const`/`fn`/`struct` at the top level so the message can appear. Right now `indexed const x = 1` gets a generic parse error.

### 4. Suggestion: shorter code shapes (for the M17 list, not this milestone)

- `list[i + 1].a = 5` (indexed): `lda i / clc / adc #1 / tax / ldy list_offsets,x`. This could be `ldx i / ldy list_offsets+1,x`, the same fold `FoldIndexOffset` does for `a[i - c]`.
- `for k in 0..4 using Y { list[k].a = k }`: `tya / sta _t / lda list_offsets,y / tax / lda _t / sta list,x`. This could be `ldx list_offsets,y / tya / sta list,x`. `LoadIndex` handles a loop variable in X but not one in Y.
- `list[i].a = list[j].a` and `list[i].a = h()` (indexed): the value goes through a temporary, but `ldx` and `ldy` do not change A, so `sta _t` and the reload are not needed. In the shift form the temporary is needed, because `lda i` clobbers A.
- `list[i].w += 1` (16-bit field): 17 instructions, with a 2-byte temporary and the index loaded twice. `main` does the same for `pts[i + 1] += 1` on a split `[u16; n]`, so this is not new.

### 5. Suggestion: one error test checks only half its message

`RecordIndexTests.cs:289` checks "more than the 256 an 8-bit offset reaches" but not the pointer suggestion that the roadmap asks for ("Step through it with a pointer").

### Spec notes (for the spec session, already raised as question 60)

- The shift shape uses X (`... / tax / lda list+off,x`), but spec 3.3 says `tay` / `,y`. Same bytes and cycles.
- `linear var` of 1-byte structs is now allowed. Before, it was the "elements are one byte" error.
- A `linear` array of 1-byte structs is still limited to 256 elements by the general rule for arrays of structs ("An array of A has at most 256 elements"), so the "over 256 bytes" index error only happens for records of 2 bytes or more. This is consistent, but 3.3 could say so.
