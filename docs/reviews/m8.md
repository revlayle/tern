## Findings

### 1. Must fix: the loop check misses arrays of structs

`src/Tern.Compiler/Semantics/Checker.cs:965`. The new check is only in the path for plain arrays. An array of structs goes through `CheckRecordIndex` (`Checker.Structs.cs:201`), which checks a constant index but not the loop counter. This compiles with no error:

```
struct E { x: u8, hp: u8 }
var e: [E; 4]
fn main() { for i in 0..8 { e[i].hp = 1 } }
```

`e[5].hp = 1` in the same program is an error ("Index 5 is past the end of 'e'"), so the two rules disagree. Spec 3.2 makes both an error. With the table layout (3.3), `e[4..7].hp` writes past the `hp` table into whatever follows, and the optimizer assumes it does not. Add the same `_loopMax` test in `CheckRecordIndex`, and a case for `e[i].hp` and `e[i].x` to the error tests.

Array fields through a pointer (`Checker.Structs.cs:178`, `p.name[i]` with `name: [u8; 4]`) have the same gap; adding the check there too keeps all array kinds the same.

Checked and caught: plain arrays, `data`, `[u16; n]`, `linear [u16; n]`, fixed-address arrays, fields of a struct variable (`p.name[i]`), `using X` loops, `const` bounds, the outer counter used inside an inner loop.

### 2. Suggestion: `cli` / `sei` from asm still make the optimizer forget everything

`src/Tern.Compiler/Backend/Optimizer.cs:162`. Any asm instruction clears the tracked state. Now that `interrupts_on()` is inline, this is the only cost left over the hand-written form:

```
x = 5
c64.interrupts_on()
y = x
```

gives `lda #5` / `sta x` / `cli` / `lda x` / `sta y`; the `lda x` is redundant. The listing already knows the effects (`; asm: reads nothing, changes I`, from `AsmEffects`). Forgetting only what an asm instruction changes (registers, flags, memory it writes) would remove the reload. Instructions that change memory, jump, or `jsr` would still forget everything. Not part of the roadmap item, so not a must fix; a benchmark could show whether it matters.

### 3. Suggestion: a redundant test in `CheckPrivateGlobalsPerRoot`

`src/Tern.Compiler/Semantics/Checker.cs:1545`. `!OwnHandler(first.Root, g)` is always true: a root for which `OwnHandler` holds is skipped at line 1542 and never stored in `firstUser`. Remove it.

## Checked and correct

- **`LargestLoopValue`.** Up: `from + (limit - from) / step * step`, so `0..=20 step 3` reaches 18 and `0..20 step 3` reaches 18. Down: always `from`. Empty ranges (`0..0`, `5..5`) give null and no error. The direction comes from `StepValue`, which the checker sets before this point (constant bounds, end `0`, or the sign of `step`). The counter is removed from `_loopMax` after the body, and each loop has its own counter symbol, so nesting and shadowing are fine. An index that is an expression of the counter (`a[i >> 1]`) is not checked, as the roadmap says.
- **Error message** names the array, its length and the loop's last value, and says how to fix it.
- **Private variables and the module's own handler** (spec 8.1). A `timer` module with `private var ticks`, its own `interrupt fn tick` and `now()` compiles and runs (`ticks` is volatile, main's loop rereads it). A handler in the main file calling `timer.now()` while main also calls it is still an error. The two roadmap cases that stay errors have tests (`Private_module_variables_used_from_two_roots_are_errors`, `A_handler_of_another_module_may_not_share_a_private_variable`).
- **`interrupts_on` / `interrupts_off`** compile to a bare `cli` / `sei` with no `jsr` (listing checked, also inside an `interrupt fn`). Called from main and a handler, they are allowed: an inline function with no memory may be shared. A call from a `for ... using X` loop is still an error, as before (an inline call counts as a call, spec 6.2).
- **`set_irq` / `set_nmi` comments** say the handler must be an `interrupt fn`.
- **Benchmarks.** The baseline did not change (1664 bytes / 535295 cycles).
