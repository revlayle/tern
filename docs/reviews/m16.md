# Review: M16, branch `m16-inline-locals`

Reviewed at `3a5e2a8`, 2026-11-07.

**Ready to merge.** No must-fix findings. 1428 tests pass (36 CPU, 1392 compiler). `BenchmarkTests` is unchanged, and the commit messages say so.

I compiled probe programs with the branch's `tern` and ran five more in the emulator, in a temporary worktree that has since been removed. They covered:

- `f(k, f(k + 1, 3))`
- `f(k) + f(k + 1)`
- an inline function with locals called from an interrupt `fn` part and from its handler
- 16-bit locals and temporaries from main and a handler under `irqEvery`
- a `for` loop inside an inline function, copied once at the top of main and once inside a caller loop
- an `indexed` struct array local with a variable index (the offset table stays one table, `f.list.offsets`)
- a `[u8; 4]` `var` line in an `inline asm fn`

All results were correct. A caller loop `using X` around an inline function that has a loop is rejected, as before ("The loop body calls a function, which can change X"). So the limitation in status.md (the counter register is chosen once per inline function) did not produce wrong code in any case I could build.

`math.min8`, `clamps8` and `max8` in main compile to the same instructions as on `main`, with zero-page operands. The program is 6 bytes shorter because the startup code no longer clears `n0`-`n2`.

## Findings

### 1. Suggestion: each inline function gets its own bytes in a caller, even when two copies never run at the same time

`CodeGen.cs:297-314`. The set of copies is keyed by (caller, inline function). Two different inline functions called one after the other in the same caller get separate bytes, although their copies are never live at the same time, except when one is nested in the other. Example:

```
import math
var a: u8
var b: u8
var c: u8
fn main() {
    a = math.min8(a, b)
    b = math.clamps8(a as i8, -3, 7) as u8
    c = math.max8(c, 9)
}
```

On `main` this used 3 work bytes (`n0`-`n2`). On the branch it uses 5 (`main.math.min8.tmp`, `main.math.max8.tmp`, `main.math.clamps8.tx/tlo/thi`). A function that calls all six helpers uses 10. Here they all go to zero page, which matters on the C64: they can push out other variables. Copies of inline functions that are not nested in each other could share bytes inside the caller's frame, as sibling functions already share frames. This is not a correctness problem, and the decision's "no cost in code or speed" holds. It is for the spec session or for M17/M18.

### 2. Suggestion: the shared-function error calls a parameter a "variable"

`Checker.cs:1937-1939`. A parameter of the inline function is reported as "the variable 'a' of the inline function 'f2'":

```
var w: u16
inline fn f2(a: u16) { w = (a << 3) + (a << 1) }
fn g2() { f2(w) }
interrupt fn h() { g2() }
fn main() { g2() }
```

The error reads `... its memory: the variable 'a' of the inline function 'f2', which is copied into it`. Without inlining, the same case says "the parameter 'a'". `v.Kind` is copied, so the message could say "parameter" for `VariableKind.Parameter`. The "hidden temporary" wording has no test either.

### 3. Suggestion: weights of the copies ignore the caller's loops

`CodeGen.cs:70`. Each copy takes the original's `Weight`. That weight was counted from the inline function's own body: the checker's uses, plus the temporaries' weights added over all copies. A helper called inside a hot loop of `main` therefore ranks for zero page as if it were called once. This was already true before M16. Now that each caller has its own copy, the weight could be counted per copy, with the caller's loop depth.

### 4. Suggestion: the flag list in `InstanceOf` is copied by hand

`CodeGen.cs:300-311`. The list covers every flag a local or parameter can have today. I checked: `volatile` is rejected on locals, and the views and the offset table resolve before the copy. A new `VariableSymbol` property that affects placement or the optimizer would be lost silently, though. A copy helper on `VariableSymbol`, next to the properties, would keep the two in step.

## Spec and documents

- Spec 6.2 still says "An inline function keeps its frame ... saves the `jsr`/`rts` but no memory" and that calling an inline function counts as a call "between roots (8.1)". 14.2 still says the feature is planned. Section 9 has no `var` lines. Spec section 10.1 still mentions the helpers' private work bytes. Status question 61 raises all of this for the spec session. The behavior matches decision 2026-11-02 (M10 review finding 5, "Later").
- The new error messages say what is wrong and how to fix it, and each has a test (`InlineTests.Reports_errors`, `InlineLocalsTests`).
