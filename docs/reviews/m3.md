## Findings

### 1. Must fix: `jmp (v)` can read its high byte from the wrong page

`Checker.Asm.cs:162-164` (the `Indirect` case) and `Allocator.cs`. On the NMOS 6502 (the C64's CPU), `jmp ($xxFF)` reads the high byte of the target from `$xx00`, not `$(xx+1)00`. The emulator models this (`Cpu6502.cs:100`). When the operand is a Tern variable, the compiler picks the address, so the user cannot see or avoid the problem. Whether the jump works depends on the size of unrelated code and data.

Failing case (zero page is filled so that `v` goes after the program):

```
var zp1: [u8; 142] @ zp
var pad: [u8; 183]
var v: u16
fn main() {
    zp1[0] = 1
    pad[0] = 1
    asm { jmp (v) }
}
```

The listing has `$0945  6C FF 09  jmp (v)`: `v` is at `$09FF`, so the jump reads the high byte from `$0900`. With `pad` at 182 or 184 bytes the same program works.

Fix: when a variable (plus offset) is the operand of `jmp (...)`, mark it like `AsmZeroPage` and have the allocator never place it so that `address + offset` ends in `$FF` (skipping one byte is enough). For a variable with a fixed address that ends in `$FF`, give an error. Add an emulator test in which the variable would otherwise land on `$xxFF`. A number written by the user (`jmp ($10FF)`) can stay as written, since spec 9 says instructions are kept as written. This will also matter for calls through pointers (6.5), which use `jmp (handler)`.

### 2. Suggestion: `jsr f` to a function with memory parameters compiles silently

`Checker.Asm.cs:216`. Assembly has no way to write `f`'s memory parameters (status question 6), so `jsr f` makes `f` read whatever is in its frame:

```
var out: u8 = 0
fn f(v: u8) { out = v }
fn main() { asm {
    lda #5
    jsr f
} }
```

This compiles without an error, and `f.v` is never written. Until the spec session settles question 6, an error would be safer, for example: "'f' takes 'v' in memory, which assembly cannot set. Pass it in a register (v: u8 using A), or call f from Tern". `jmp f` has the same problem. `#f.lo` (taking the address) can stay allowed.

### 3. Suggestion: `keeps` without `@` gives a parse error

`Parser.cs:168-187`. `fn f() keeps X { }` reports "Expected '{', found 'keeps'". A clearer message would be: "'keeps' is only for routines at a fixed address: fn f() @ $addr keeps X". Add it to the error tests.

### 4. Suggestion: one new error has no test

`Checker.Asm.cs:80`: "Only numbers can be negated or inverted" (e.g. `lda -score`). All the other new errors have tests, in `AsmTests`, `RoutineTests`, `DataTests` and `ErrorTests`. CLAUDE.md says new errors go in `ErrorTests.cs`; the per-feature files read well, but either the tests or the convention should change so they agree (the convention is the spec session's call).

### 5. Suggestion: register overlap is checked by comparing strings

`Checker.cs:161` (`ret.ToString().Contains(reg.ToString())`) and `Checker.cs:963` (`pr.ToString().Contains(held.ToString())`). This works for the current `Register` names (`Carry`, `Zero` and `Negative` have no capital A, X or Y), but it breaks silently if a name is added or renamed. A small helper (`Register.Uses(Register r)`, mapping `AX` to `{A, X}` and so on) used in both places would be clearer.

### 6. Suggestion: a keyword right before a quote becomes an encoding prefix

`Lexer.cs:158`. Any word before a quote is read as a prefix, including keywords: `return'A'` gives "Unknown encoding 'return'". Checking `Keywords` first would keep keywords working without a space. Rare in practice.

### 7. Suggestion: stray blank line

`Checker.cs:140-141`: a second blank line was added after the `ReturnUsing` check in `DeclareFunction`.

## Probes (all correct)

Compiled and read the listings; checked the KERNAL example in VICE.

- `for i in 0..n using X { chrout(s[i]) }`: `txa / tay / lda (s),y / jsr $FFD2`, no temporaries, X kept across the call.
- Arguments that need an index register inside `using X` and `using Y` loops: `chrout(arr[i] + arr[j])` uses the free register for `j`; `put(arr[m] + 1, arr[j])` (A and Y parameters, X loop) loads Y last, after A. The new "compute straight into A" path never clobbers A: X/Y loads after it are always memory operands, and register sources (a loop variable for an X parameter) go through a temporary.
- `keeps A` on a routine that returns in A is an error. A loop register passed as a parameter is an error.
- `jsr main` in an asm block is reported as recursion. `jsr` and `#f.lo` add callees, so frames do not overlap.
- `lda (v),y`, `stx v,y`, `ldx v,y` force `v` into zero page; too large a variable gives the "Zero page is full" error that names the asm use. `data` used with `(tbl),y` goes to zero page and is filled at startup, as for dereferenced pointers.
- Asm in a `using X` loop: `txa`, `ldy`, `jmp .label` and `jsr chrout` (keeps X) are allowed; `jsr $FFD2` (an address, so nothing is known to be kept) is an error at the instruction.
- Lexing: `;` gives the intended error; `//` and `/* */` comments; upper-case mnemonics; `ASL A`, `asl` and `rol a` with a variable named `a`; `#<msg` gives the `.lo`/`.hi` hint; `.l: dex` on one line; empty `asm {}`.
- `for _ in 0..10` keeps its counter in memory, so asm blocks in such loops cannot break it.
- Encodings: spot-checked `screen` and `screen_mixed` against the C64 tables (`a`-`z` to `$01-$1A`, `A`-`Z` to `$41-$5A` in mixed; `[` to `$1B`; `π` to `$5E`).
- Spec 11: `chrout(x)` with `fn chrout(...) @ $FFD2` is `lda x` / `jsr $FFD2`.
