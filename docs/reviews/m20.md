## First review

Reviewed at `ee66b2f`, 2026-11-08 (commits `bf5cb89` to `ee66b2f`).

**Not ready to merge.** One must-fix finding: the index check misses an index into a `linear` array once the scaled index wraps, so `pts[130]` on a 10-element array runs clean. Everything else is correct. The signed loops held up against 7200 random loops compared with a model, and the shapes match spec 11. 1999 compiler tests and 36 CPU tests pass. No benchmark changed (1254 / 350780).

What I checked beyond the tests:

- **Signed loops, differential fuzz.** A script generated 120 programs with 60 loops each: `i8` and `i16` counters, `a..b`, `a..=b`, steps ±1, ±2, ±3, ±5, ±7, ±64, ±100, `a..0`, `a..=0`, a literal start or end with a variable on the other side (including literals that widen an `i8` bound to `i16`, such as `n..=200`), in X, in memory, and passed to a call. The bounds were edge values (-128, -127, 126, 127, -32768, 32767, 0, ±1) and random values. Each loop's count and the sum of its values matched a Python model of spec 5.1 (stopping when the step would leave the type). No failures, and the index check stayed quiet on all of them.
- **Spec 11 shapes.** I compiled each signed row. `-10..10 using X`: `ldx #$F6` … `inx / cpx #$0A / bne`. `n..=0`: `ldx n / bmi` … `dex / bpl`. `n..0`: `ldx n / beq / bmi` … `dex / bne`. `a..b`: `sec / sbc / bvc / eor #$80 / bpl`, then the unsigned loop. `a..b step 3`: `lda b / eor #$80 / sta e` before the loop, then `txa / clc / adc #$03 / bvs / tax / eor #$80 / cmp e / bcc`. All match the spec. A 16-bit `w..=0` branches on the N flag of `lda w+1` before the store, with no extra test. A signed `a..=b` ends in `inx / jmp`, where the unsigned loop has `inx / bne` (always taken there). The signed form needs the `jmp`, because a signed counter can step through 0.
- **The index check.** Every indexed instruction that CodeGen emits now goes through `Indexed` or `MatchCheck` (a grep finds no unmarked `AbsoluteX`/`AbsoluteY` emission). Because the check is on the address actually accessed, the optimizer's copies of an operand (`ReadCopiesFromSource`) stay correct. I found no false alarms on valid accesses to linear, indexed and split struct arrays, a 256-byte ring buffer with `buf[head + 1]` at 255, or `small[(i + 3) & 3]`. `small[k - 1]` with k = 0 is reported as index 255. An `i8` `indexed match` with -7 against -4..3 is reported as -7, the run stops, and the exit code is 2.
- **C-habit errors.** I tried `*p = 1` as a statement, `"c++"` inside a string, `x--` after a `// x++` comment, `(x++)`, a split `3 +\n+x`, keywords as a struct field and as a const name, and `%1111_0000`. All give the expected message, or compile when they should.
- **`x += 2`.** On a variable that a `while` loop holds in X, the change does not apply: the code is `txa / clc / adc #$02 / tax`, and the result is correct. A volatile byte keeps the add.

### Findings

1. **Must fix: a scaled index that wraps escapes the check** (`CodeGen.cs:102-111`, `IndexChecker.cs:52-58`). For a `linear` 16-bit array the index is doubled (`asl / tax`), and for a linear struct array it is multiplied by the record size. The check looks only at X after the scaling, so an index whose scaled value wraps past 255 lands back inside the table and is not reported. Failing cases (each `tern run` prints no index check and exits 0):

   ```tern
   linear var pts: [u16; 10]
   var j: u8 = 130          // X = 260 & 255 = 4, which is pts[2]
   var out: u16
   fn main() { out = pts[j] }
   ```

   ```tern
   struct E { x: u8, y: u8, hp: u8, k: u8 }
   linear var es: [E; 10]
   var j: u8 = 66           // X = 264 & 255 = 8, which is es[2].hp
   var out: u8
   fn main() { out = es[j].hp }
   ```

   With `j = 12`, `pts[j]` is reported, so only the wrap is missed. That takes an index of 128 or more for `u16` elements, and 64 or more for 4-byte records. A runaway index (garbage, or a wrapped `i - 1`) is exactly the kind of bug this check is for. Roadmap M20 and spec 14.4 say the check reports a variable index outside its array, with no exception. Fix: mark the instruction that scales the index (the first `asl` of A, or the `lda` of the index before it) with a check that the unscaled index is below the element count, as the offset table read of an `indexed` struct array is checked now. Add the two programs above to `Every_kind_of_array_is_checked`. If it cannot be done cheaply, ask the spec session to accept the limit and document it in spec 3.2 and `SKILL.md`.

2. **Suggestion: the SKILL.md exit code for a match value is wrong** (`.claude/skills/tern/SKILL.md:50-52`). "an index outside its array, and an `indexed match` value outside its patterns (which also stops the run), are printed with the source line, and the exit code is 3". A match value stops the run before main returns, so `tern run` exits 2 (`Cli.cs:154`, and my run of the example above). `tern --help` gets it right. Write "the exit code is 3 (2 when an `indexed match` value stopped the run)".

3. **Suggestion: one 16-bit access is reported twice** (`IndexChecker.cs`). `w = p[i]` on a `linear` or split `u16` array gives two identical lines, one for the low-byte read and one for the high-byte read (`Every_kind_of_array_is_checked` expects 2). In `tern run` output this reads as two errors. Report one error per source line and message, or merge the high table's error into the low table's, so that each access gives one error.

4. **Suggestion: two C-habit fixes name the wrong thing** (`Lexer.cs:207-211`, `Parser.cs:970-971`).
   - `a[i]++` gives "Write 'x += 1'". There is no `x` in the program. The source text of the operand is easy to get, so write "Write 'a[i] += 1'". If the operand's text is not at hand, "Write '+= 1' instead" works too.
   - `%2` gives "Write binary numbers as 0b2", and `%0xFF` gives "0b0". Only give this error when the number is made of 0, 1 and `_`. Otherwise keep the generic error, or the `%` operator's own error.

5. **Suggestion: a doc comment moved to the wrong method** (`CodeGen.cs:93-101`). `Indexed` was inserted between `HighTable`'s `<summary>` and `HighTable`, so `Indexed` now has two summaries and `HighTable` has none. Move the first summary back above `HighTable`.

6. **Suggestion: `using X` on an `i16` counter gives a message with no fix** (`Checker.cs:1063`). M20 makes this error reachable for signed counters (`for i in -300..300 using X`): "A i16 loop variable does not fit in X". It reads "A i16", and it has no fix sentence (CLAUDE.md: every error ends with one, which `--json` reports as the suggestion). Write "An i16 loop variable does not fit in X. Remove 'using X', or use bounds that fit in an i8". The `u16` case has the same text.

7. **Suggestion (later): `v += 2` on a variable held in a register.** Shown above, it is `txa / clc / adc #$02 / tax` (4 bytes, 8 cycles). `inx / inx` is 2 bytes and 4 cycles. This is outside M20's scope (the roadmap asks for memory), but it fits next to the held `v += 1` → `inx` of M18.

8. **Note: `tern bench` does not print the errors.** It is listed under "Not done" in `status.md`. The roadmap asks only for `Run.Program` and `tern run`, so this is fine for M20. A wrong index in a benchmarked variant gives misleading cycle counts, so a later milestone should print the errors there too.

Questions 76-78 in `status.md` ask the spec session about provisional choices: the keyword error's wording, `x += 2` on `i8`, and what a run does after an index error. None of them blocks the merge. The behavior as built is consistent, and the tests cover it.
