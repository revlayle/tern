Batching the removals is safe:

- **Register and memory values.** A removed load, store or transfer changes no register or memory value, so the analysis still holds for every later instruction in the pass.
- **Removals justified by "N and Z already match".** These change nothing, flags included.
- **Removals justified by "N and Z are dead".** These change the flags only on the straight run of code after the removed instruction, up to the next instruction that sets both N and Z. `NzLiveAfter` treats every jump and branch as a read, so that run has none, and every point on it has a higher index. ## Findings

### 1. Must fix: a parameter kept in Y breaks other pointer accesses

`src/Tern.Compiler/Backend/CodeGen.cs:180` (`KeptRegister`). The parameter is kept in Y whenever the body has no call, asm block or register loop and never assigns it. The body's pointer accesses are not checked. A pointer access whose index is not exactly the parameter must load Y, and `LoadPointerIndex` (`CodeGen.cs:1385`) then throws an error that does not fit the program:

```
var buf: [u8; 8]
var p: ptr u8
fn f(n: u8 using Y) {
    p[3] = n
}
fn main() {
    p = addr(buf)
    f(2)
}
```

```
3:24: p[i] needs the Y register, which holds a loop variable. Use 'using X' for that loop
```

There is no loop, and the user cannot fix it. On `main` this compiles (`n` is stored as `f.n`). `res = p[2] + n as u16` with a `ptr u16` fails the same way. `ChooseCounterRegister` already solves this for loop counters with `CountPointerIndexes` (Y only if every pointer access is `p[counter]`). Apply the same rule here: keep a Y parameter only if the body has no other pointer access, and otherwise store it as before. Add tests to `A_parameter_is_stored_when_the_body_needs_the_register`: `p[3] = n`, and a `ptr u16` access, each run and checked.

A parameter kept in X has no such problem. I tried `p[k] = a[j]`, `p[a[j]] = a[k]`, `a[p[k]] = a[j]`, `a[j] = p[a[k]]`, `p[k] += a[j]`, `a[j] += p[k]`, a dense `match`, `for` with the parameter as bound (`0..n`, `n..0`, `0..=n`), `while c < n`, `j - n` and `w - n as u16`. All compile and give the right results, and so do the same statements in automatic counter loops.

### 2. Suggestion: the optimizer's run time grows with the cube of function size

`src/Tern.Compiler/Backend/Optimizer.cs:20` and `:283`. `RemoveOneRedundant` removes one instruction, then analyses the whole function again. Each analysis copies state sets per item, and `NzLiveAfter` scans forward from each candidate. Compile time for a `main` made of n copies of `x = k` / `y = x` / `z[x & 3] = y`:

| n (statements) | compile time |
|---|---|
| 300 | 0.13 s |
| 600 | 0.66 s |
| 1200 | 2.7 s |
| 4500 | 228 s |

A long `main` (a game's setup code or a level table filled in code) can reach this size. Remove every redundant instruction one analysis finds, then analyse again until nothing changes. Two adjacent removals interact only through N/Z: a load removed because a later load sets N/Z, and that later load removed because the first set them. Either skip a candidate whose N/Z argument depends on another removal in the same pass, or check N/Z liveness again after each removal (a local scan, without a new analysis). A test that compiles a function of a few thousand statements within a time limit would catch a regression.

### 3. Suggestion: `kernal_off` switches the ROM out before the NMI vector is set

`src/lib/c64/c64.tern:144`. `sta $01` comes before `sta $FFFA` / `sta $FFFB`. In between, RESTORE (an NMI, which `sei` does not hold off) jumps through whatever RAM holds at `$FFFA`. Writes to `$FFFA` reach the RAM under the KERNAL even while the ROM is visible, so writing the vector first and `$01` last closes the gap. The window is about 10 cycles, so this is rare, but the fix is moving two lines. `set_nmi` cannot avoid a similar window between its two writes; its comment already says so.

### 4. Suggestion: four more statement walkers

`CodeGen.cs`: `AllowsRegisterParameter`, `ContainsLoop`, `ContainsReturnValue` and `CountPointerIndexes` each repeat the same switch over statements and expressions. `ContainsCall`, `AlwaysReturns`, `ContainsBreak` and `AssignsVar` already do the same. One helper that lists a node's children (or a `Descendants(node)` enumerator) would make each of them a short `Any`/`Count` and avoid a node kind missing from one of them later. `AllowsRegisterParameter` is also used for loop counters, so a name such as `KeepsIndexRegistersFree` would read better.

## Checked and correct

- **Dataflow.** States meet at labels. Labels named other than by a jump or branch (jump-table targets, `#label.lo`) start unknown. `jsr` and every asm instruction forget everything. A write through a pointer or to a numeric address forgets all memory. A write to a callee's frame forgets every callee frame. Fixed-address writes forget all fixed-address variables. Views map to their storage (`CodeGen.Var`), so a write through one field forgets the whole struct. Temporaries are the same symbol when reused. Every load the CPU executes sets N and Z, so the `Flags` tracking is right. A load is removed only when N/Z already match or are dead; `jsr`, `rti` and a plain `rts` end liveness, except for `-> bool using zero/negative`. Callers never rely on N/Z after a call: `if f() == 0` and `if f() != 0`, with `f` changing another variable just before `return t`, give the right result in the emulator.
- **Volatile memory** (spec 4). Loads and stores of volatile variables are never tracked or removed. A view takes its storage's volatility. A handler that changes a global only in an asm block (`inc counter`) makes it volatile, and main's wait loop reloads it on every pass (listing checked).
- **Unreachable code.** Asm instructions are never removed. Jump-table targets are reached through `LabelTable`.
- **Automatic loop counters.** Checked with calls in the bounds (evaluated before the counter is set), a dense `match`, 16-bit and struct arrays, `return` from inside the loop in an inline function returning `using X`, and `u16` returns in AX. All results match `main`.
- **Frames.** Isolated frames come after every other frame. A function with no memory that is shared between roots gets offset 0 and has no frame. Handlers still follow main's tree.
- **Fixed-address overlap check.** `ramEnd` is inclusive. The zero-page check covers only the bytes the compiler actually placed, as the spec says.
- **Errors.** Every new error has a test: `addr(f)` (`FunctionAddressTests`), `volatile` and the overlap checks (`VolatileTests`), shared functions (`InterruptTests`).
- **Benchmarks.** `BenchmarkTests` fails on any change in bytes or cycles, better or worse. Totals: 1802 / 667366 before, 1664 / 535295 now (−8% bytes, −20% cycles).
- **Code shapes** (spec 11). Unchanged, or shorter where the optimizer applies (`a[i] = v` keeps the same instructions in a different order, same length).
