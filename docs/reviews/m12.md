The findings below are cases the tests do not reach. I found each one by compiling a small program and reading its listing.

### 1. Must fix: data at the start of the first program area moves the BASIC line or the jump table

`Assembler.cs:125-126` lays fixed sections first, then puts the other sections first fit in what is left. When fixed data sits at the start of the first area, the `startup` section (BASIC line included) or the binary's `jump table` section moves past it. Nothing reports this.

Main program:

```
data first: [u8; 3] @ $0801 = [1, 2, 3]
fn main() { }
```

This compiles with no error. The listing has the data at `$0801`, the BASIC line at `$0804` and `start` at `$0810`. The file loads at `$0801`, so BASIC finds `01 02 03` where its link pointer should be, and the header's `SYS 2061` jumps to `$080D`, which is inside the header bytes. The program crashes. The check at `TernCompiler.cs:64` looks only at `layout.Program[0].First`, not at where `start` landed.

Binary:

```
memory { $C000..=$CFFF program }
export play
data first: [u8; 3] @ $C000 = [1, 2, 3]
fn play() { }
```

The jump table is at `$C003`. Spec 12.3 puts it "at the beginning of its first `program` area". The api file follows the moved table, so a Tern host still works, but a host written any other way calls `$C000` and runs the data.

Fix: place the startup/jump-table section at the first area's start before anything else. Fixed data that overlaps it is then an error ("'first' at $0801-$0803 overlaps the BASIC line and startup code at $0801-..." / "...the jump table at $C000-..."). Add a test for each.

### 2. Must fix: variables in a region inside a `volatile` range are not volatile

`Checker.cs:79` marks only `FixedAddress` globals in volatile ranges. A `@ region` variable has `Region` set, not `FixedAddress`, so it is never marked. Spec 8.4 says a `volatile` range "may lie in any other kind", and decisions (2026-11-02, volatile memory) say volatile depends on where the memory is. A region inside a platform volatile area (`$D000-$DFFF`) has the same gap.

```
memory {
    $C000..=$C0FF  region shared
    $C000..=$C0FF  volatile
}
var flag: u8 @ shared
var other: u8
fn main() {
    var a = flag
    var b = flag
    other = a + b
}
```

The listing reads `flag` once: `lda flag` / `sta main.a` / `sta main.b`. The second read is dropped. Fix: set `InVolatileArea` after the allocator gives region variables their addresses, or check the whole region range against the volatile ranges when the variable is declared. Add a listing test next to `A_volatile_line_makes_fixed_address_variables_in_it_volatile`.

### 3. Must fix: a `program` line may overlap the free zero page, and code and variables then share bytes

`MemoryLayout.cs:93` keeps the platform's zero page when the block has no `zeropage` line. It subtracts only reserved and region ranges, not `program` lines. The overlap check (`MemoryLayout.cs` `claimed`) does not see the platform's zero page either.

```
memory { $0002..=$7FFF program }
export play
var p: ptr u8 = 0
fn play(v: u8 using A) { p[0] = v }
```

This compiles. The jump table is at `$0002`, and so is `p`. `setup` begins `lda #0` / `sta p` (`$02`), so it overwrites its own jump table. A program area below `$0100` is unusual, but the compiler writes broken code with no error. Fix: either subtract `program` ranges from the platform zero page, like `reserved` and `region` ranges, or report an error when a `program` line overlaps the zero page the compiler will use. Add a test.

### 4. Must fix: a fixed-address variable may overlap a variable the compiler placed in a region

`CheckFixedAddresses` (`TernCompiler.cs:242`) checks fixed variables against the program areas, fixed data and zero page, but not against region variables:

```
memory { $C000..=$C0FF region buf }
var a: [u8; 16] @ buf
var b: u8 @ $C004
fn main() { a[4] = 1  b = 2 }
```

This compiles, and `b` is `a[4]`. Decisions (2026-11-02): "A fixed-address variable overlapping the program or its variables is a compile error", so a growing region does not overwrite it silently. Region variables are the compiler's placements, so the same rule applies. Fix: check against `plan.RegionUse`, using the existing message shape. Add a test to `MemoryTests.Reports_errors`.

### 5. Suggestion: the api module's `ZP_*` is one span over every zero-page range

`TernCompiler.cs:166-169` gives one range from the lowest to the highest zero-page byte used. With `$02..=$03 zeropage` and `$FB..=$FE zeropage` and three pointers, the api says `ZP_FIRST = $02`, `ZP_LAST = $FE`. A host that reserves that range, as the api's comment tells it to, loses all of its own zero page, though the binary uses only 6 bytes. This is safe but costly. Write one constant pair per used zero-page range (`ZP_FIRST`/`ZP_LAST`, `ZP2_FIRST`/`ZP2_LAST`, ...), or one per declared `zeropage` line that has a used byte.

### 6. Suggestion: the api module leaves out fixed-address memory the binary uses

Spec 12.3 asks for "constants for every range the binary uses". A binary with `var t: u8 @ $FB` or `var buf: [u8; 4] @ $C800` uses those bytes, but the api module has no constant for them. Neither does a `reserved` range of the binary, which might hold its buffers. Hardware registers should not be listed, so a reasonable rule is: fixed-address variables outside the volatile areas, and the binary's `reserved` lines. If this is left as it is, `docs/status.md` should say so, and so should the developer guide list in the roadmap.

### 7. Suggestion: small points

- The error for a main program whose first area is not `$0801` says "Start the first 'program' line of the memory block at $0801", even when the block has no `program` line (`memory { $0800..=$08FF reserved }`, tested in `Reports_errors`). There the fix is to move the `reserved` range.
- Region clear loops are labeled `$"clear_{First:X4}"` plus the page number, so page 0 of a region at `$C000` is `clear_C0000`. A separator (`clear_C000_0`) would read better in listings.
- `CompileResult.HaltAddress` is `-1` for a binary, since `halt` is never defined. A comment on the property would help.
