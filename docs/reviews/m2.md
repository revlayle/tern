## Findings

### 1. Must fix: `p[i] = v` with `i` in X spills A to a temporary

`CodeGen.cs:1062` (`PointerByte`). For a store, the value is computed into A first and the index second. When the index load changes A, the value is saved to a temporary and reloaded. This happens whenever the index is a `using X` loop variable, because `txa`/`tay` goes through A:

```
for i in 0..4 using X { d[i] = v }
```

gives 6 instructions:

```
lda v / sta _t0 / txa / tay / lda _t0 / sta (d),y
```

Spec 11's shape loads the index first (`ldy i` / `lda v` / `sta (p),y`). With `i` in X that is `txa` / `tay` / `lda v` / `sta (d),y`: 4 instructions, 6 bytes and 6 cycles shorter per iteration. Design rule 4 says generated code must match spec 11 or be shorter.

The copy loop `for i in 0..n using X { d[i] = s[i] }` is worse: 8 instructions (`txa/tay/lda (s),y/sta _t0/txa/tay/lda _t0/sta (d),y`), where 4 are enough. `p[i] += 1` with `i` in X has the same spill. `using X` is the form that the "needs the Y register" error recommends, so users will be steered into this.

Fix: when computing the value does not use Y (constants, variables, array reads by X, no pointer reads or calls), load Y first and then the value, as in the spec shape. Add a listing test for `d[i] = v` with `i` in X. Removing the second `txa`/`tay` in the copy loop is already listed as an M7 item ("Y is reloaded for every pointer access") and can wait; the spill should not.

### 2. Suggestion: missing error tests

Three new errors have no test in `ErrorTests.cs` / `DataTests.Reports_errors`:

- `Checker.cs` `ResolveType`: "A pointer must point to a number, bool or pointer" (`var p: ptr [u8; 4]`).
- `Checker.cs` `IncludeBytes`: "'x' is empty" (an empty file).
- `Lexer.cs` `ReadQuoted`: "Character literal is not closed with '''" (`var c: u8 = 'A`).

### 3. Suggestion: storing a 16-bit value into a split array always goes through a temporary

`CodeGen.cs:364-383`. `rows[0] = addr(buf)` gives 8 instructions (value to `_t0`, then `_t0` to `rows`/`rows+2`) where 4 are enough (`lda #buf.lo / sta rows / lda #buf.hi / sta rows+2`). This is M1 code (the same happens for `ws[0] = w`), but M2 makes it more common because pointer tables are arrays of `ptr`. `StorePointerWord` already uses `Simple2(value)` to skip the temporary; the split-array store could do the same.

### 4. Suggestion: a user function named `addr` is accepted but never called

```
fn addr(x: u8) -> u8 { return x }
fn main() { var n: u8 = addr(n) }
```

The declaration is accepted, but the call is taken as the built-in, giving "Expected u8, found ptr u8". The same probably applies to `len` and `sizeof` from M1. Declaring a function (or variable) with a built-in's name should be an error such as "'addr' is a built-in function; choose another name".

### 5. Suggestion: error messages that could say more

- `var p: ptr u8 = addr(d)` (global initializer) gives "A global's initial value must be known at compile time". This limitation is documented in `status.md`; the message could say "addr() cannot be used in an initial value; assign it at the start of main".
- `data d = [1, 2, 3]` gives "Array variables need a written type, e.g. [u8; 4]". For `data` it should say "data" rather than "variables".
- `screen'A'` gives "Expected end of statement, found 'A'". Until spec question 8 is answered, a direct message ("screen'A' is not supported; use screen\"A\" or the screen code as a number") would help.
- Escape errors (`Unknown escape '\q'`) point at the start of the string, not at the escape.

### 6. For the spec session (not code findings)

The questions in `status.md` are reasonable and the provisional choices are consistent with the code. Two need an answer before more code depends on them:

- **Q1, type of `addr()`.** Spec 10 says `u16`, spec 3.4 implies a pointer, the code returns `ptr T`. The spec should be made consistent.
- **Q3, `p[i]` on `ptr u16`.** A variable index of 128 or more wraps silently (`asl` drops the top bit), while a constant index of 128 is an error. If the spec keeps this, it should say so in 3.4.

## Probes run

All compiled and run in the emulator, results checked by hand:

- `p - 1`, `p - d` (u8 var), `p + w` (u16 var) across page boundaries: correct borrow/carry.
- `ptr u16`: `wp[i] = wp[j] + 1`, `wp[2] += 1` wrapping `$FFFF` to `0`, `wp[0].hi = 7`: correct.
- `ptr i8` read sign-extended into `i16`: correct.
- `a < b`, `b <= a` across the high byte (`$10FF` vs `$1100`): correct.
- `bp[bp[0] - $EE] = 99` (index reads through the same pointer): correct.
- `rows[k][i] = i + 1` inside `for ... using X` (computed pointer, zero-page temporary, Y used for `rows[k]`): correct.
- Frame sharing: sibling functions `g` and `h` share their zero-page pointer at `$05`; the caller's pointer stays separate.
- Errors: unary `-`/`~`/`!` on pointers, pointer as a condition, pointer loop bounds, shifting a pointer, `p + (-1)`, data assignment, mixing pointer types: all give clear messages.
- Lexer: apostrophes in comments, `//` inside a string.
- Code shapes: `x = p[i]` is `ldy i / lda (p),y / sta x`; `p += 1` is `inc/bne/inc`; `p = p + 40` is `clc/lda/adc/sta/bcc/inc`; `put(p: ptr u8 using AX, ...)` dereferences the parameter directly. `for ... using Y { d[i] = s[i] }` is the optimal `lda (s),y / sta (d),y`.
- `examples/hello.tern` in VICE (`x64sc -autostart`): "HELLO FROM TERN" in rainbow colours, centred, on a black screen.
