## Part 3, first review (registers across loops and layout: F7/F11/F15, F13, F9, F12)

Reviewed at `1b4160d`, 2026-11-07 (commits `bf592b9` to `1b4160d`).

**Not ready to merge.** One must-fix: F12's page placement can move the variables onto a fixed-address variable, so a program that compiles on `main` is now rejected. Everything else is correct as far as I could find. 1682 compiler tests and 36 CPU tests pass. Each commit gives its benchmark delta (1311 / 363980 -> 1259 / 351130), and `comparison.md` has the new totals (Tern 968 / 341,969).

### Findings

#### 1. must fix: page placement can put the variables on top of a fixed-address variable

`TernCompiler.cs:76-165`, `Assembler.cs:219-227`. The assembler moves the variable block forward to the page offset it was asked for. It checks only that the block fits in the program area and that no `jmp (v)` vector ends a page. It does not check fixed-address variables in that area. `CheckFixedAddresses` runs after the placement loop (line 165), so an overlap there is a compile error. It does not fall back to placing the variables one after another.

Failing case:

```
var arr: [u8; 250]
var gfx: [u8; 16] @ $0980
var total: u8
fn main() {
    gfx[0] = 1
    for i in 0..250 { total += arr[i] }
}
```

- `main`: compiles; the variables are at `$0837-$0930`.
- Branch: `error: 'gfx' at $0980-$098F overlaps the program and its variables at $0801-$09F9. Move 'gfx', or make the program smaller`. `arr` moved to `$0900` to start a page.

This is a common C64 setup: sprite or character data at a fixed address just past a small program. The roadmap says to place the arrays "when there is room", and the status says "if there is none ... the variables one after another, as before". Here there is no room, but the program fails instead of falling back.

Fix: treat an overlap with a fixed-address variable like having no room. For example, run the fixed-address check inside the loop and retry with `byPage = false` when page placement caused the overlap, or give the assembler the fixed-address ranges as used memory. Add a `PagePlacementTests` case like the one above: it compiles, and the variables follow each other.

#### 2. suggestion: count only indexed reads, not stores

`TernCompiler.cs:76-80` collects every `abs,X` / `abs,Y` operand, stores included. A store never pays for a page crossing. So an array that is only written through an index still gets placed, and RAM is left free for nothing:

```
noinit var buf: [u8; 250]
var out: u8 @ $C000
fn main() {
    for i in 0..250 { buf[i] = i }
    out = buf[249]
}
```

Here `buf` goes to `$0900`, and the listing says "218 byte(s) left free so that indexed reads of the variables do not cross a page". The only indexed access is `sta buf,x`. The status and the `Allocator` comments say "arrays the code reads through an index register". Filtering with `AsmEffects.ReadsMemory(i.Mnemonic, i.Mode)` would match that. It would also make finding 1 less likely to come up.

#### 3. suggestion: indentation of the retry loop

The `try` / `catch` in the placement loop (`TernCompiler.cs:152-162`) is indented one level less than its body. Formatting only.

#### Not findings, for the record

- `Allocator.cs:190`: `ZeroedSize -= lead` makes the size negative when there are no zeroed globals and the first placed array is `noinit` with a read below its start. `Startup` clears only when `ZeroedSize > 0`, so this is harmless.
- **Registers held across loops** (F7/F11, F13), checked in the emulator against C# on extra programs:
  - a held variable beside a counter kept in memory (`step 2`) and a second index that is not held
  - `indexed` and `linear` struct arrays, a `linear [u16]` read, `a[k] += 1` with `k` not held
  - a `match` jump table with a pointer access
  - an outer counter beside an inner `for _` repeat, and beside inner loops with pointer and array accesses
  - struct-pointer fields (`e.hp`) in outer and inner bodies (they count as pointer accesses, so the outer counter takes X)
  - every compound assignment (`<<= >>= &= |= ^= += -=`, with constants and a variable) on a variable held in Y

  All are correct.
- **Stores moved out of loops** (`SinkStoresFromLoops`):
  - Every way out of the loop is covered: falling out at the end (after the labels only the loop jumps to) and jumps to outside labels.
  - `Analyse`'s state at a label merges every path into it, so the register chosen for the exit store holds the value on all of them.
  - A jump table, return, call, or jump out of the code turns the change off.
- **Dead stores into globals** (F7): the `Live.Globals` / `Dead` union is right in all four combinations. Calls, `rts`, `rti`, jumps out, the end of the code, and reads through a pointer or at a number all count as reads.
- **Loop control** (F9): `FirstTestTrue`, `DecrementTest` (also `w.hi` with `w -= 256`, and `dex` for a held variable), `NonEmptyInside`, and unsigned `x > 0` as `x != 0` all give the right results at the edges. That includes a `while` whose variable starts at 0, and `m >= 250` wrapping at 255.

## Findings

### 1. must fix: a volatile index is read twice by the 16-bit in-place shapes

`CodeGen.IndexedOperand(e, 2)` (`CodeGen.cs`, around line 1004) returns an action that calls `LoadIndex(index)` on every use. The 16-bit users call it once per byte:

- `Binary16InPlace`: `l(Lda, 0) ... l(Lda, 1)`, and `store(Sta, 0)` / `store(Sta, 1)` for an element destination
- `Compare16`'s `Side`
- `ShiftedOperand16`: `x(m, 0)` / `x(m, 1)`

So the index is loaded twice. For ordinary memory the optimizer removes the second `ldx`. A volatile index stays. Spec 4 says "Every read and write of volatile memory in the source happens exactly once", and `main` reads it once.

Failing case:

```
volatile var vi: u8
var j: u8 = 2
var k: [u16; 4] = [1, 2, 3, 4]
var w: u16 = 5
fn main() {
    k[vi] = k[j] + w
    w = k[vi] + w
    if k[vi] < w { }
}
```

| | `main` | `m18-fixes` |
|---|---|---|
| `k[vi] = k[j] + w` | one `ldx vi` | two: `ldx vi / sta k,x` … `ldx vi / sta k+4,x` |
| `w = k[vi] + w` | one `ldx vi` | two |
| `k[vi] < w` | one `ldx vi` | two |

A volatile index is usually a counter that a handler changes. If it changes between the two reads, the low and high bytes come from different elements.

Fix: in `IndexedOperand`, return null for `size == 2` when the index reads volatile memory. The old paths then load the index once. Add a listing test that `ldx vi` appears once per access in each of the three shapes.

The 8-bit uses of `IndexedOperand` load the index once and are fine.

### 2. must fix: `RemoveDeadLoads` has no tests of its own

`Optimizer.RemoveDeadLoads` is a new pass with its own rules:

- `rts` reads only the return value's registers, and N/Z for `-> bool using zero` or `using negative`
- a load from a fixed address stays
- a volatile load stays
- branches, calls and assembly end the search

No test names it or checks these rules. It is covered only indirectly, through `fib16`'s benchmark and `Constants_stored_together`. The roadmap asks for correctness tests and a listing test for every fix.

The `rts` rule is the risky one. Removing a load of A in front of the `rts` of a `-> u8` function would be wrong code, and no test would catch it. My probes of `-> u16` (`ldx #0` kept), `-> u8` and `-> bool` returns were correct.

Add tests for:

- a dead `lda #c` removed, in the listing
- a load before `rts` kept for each return register (A, AX, `using zero`) and removed when the register is not returned
- a load from a fixed-address variable and from a `volatile` one kept
- a load followed by a branch or `jsr` kept

### 3. suggestion: spec 11's `-x` row is now longer than the code

Spec 11 gives `-x` (u8) as `lda x / eor #$FF / clc / adc #1`. The branch emits `lda #0 / sec / sbc x`. That is shorter (5 bytes and 7 cycles, against 7 bytes and 9 cycles), so it is allowed. For the spec session: update the row so the table states the real cost.

Likewise, `x = 0` at the start of `main` now generates no code (`RemoveStoresOfStartupZeros`). The spec session may want to mention this next to the `x = 0` row or in 8, since the cost of the statement now depends on where it is.

### 4. suggestion: `GroupConstantStores` moves every source line of a run to its front

`Optimizer.cs`, `GroupConstantStores`: `grouped = run.Where(item => item is Comment or SourceLine)`. A run of three assignments then lists all three source lines first and then all the code, so the listing no longer shows which instruction belongs to which line.

This is not wrong, but `.lst` files are the main way to read code cost (rule 1). Consider keeping each source line in front of the first store it owns, or limiting a run to one statement plus the argument stores of a call, which is where the savings are (`mul(123, 45)`).

### 5. suggestion: `CounterMax` repeats the checker's largest loop value

`CodeGen.CounterMax` works out a bound from the loop header. The checker already computes `LargestLoopValue(from, to, inclusive, step)` for constant bounds (`Checker.cs` line 1063, `_loopMax`). For constant bounds with a step, `CounterMax` gives `to` (or `to - 1`), which is looser than the checker's last value (`0..=250 step 7` has 245 as its last value).

One function used by both would be shorter and a little stronger. `CounterMax` would keep only the two cases the checker does not cover: a constant start counting down, and a variable `u8` end.

### 6. suggestion (pre-existing): for a simple index, the index is still read after the value

Spec 5 (evaluation order): "In an assignment to an indexed place (`a[i] = v`, …), the index is evaluated before the value." For `k[vi] = k[j] + w`, both `main` and the branch load `vi` after the value is computed. The difference is observable only for a volatile index or value. This is not caused by this branch. I am noting it because finding 1 touches the same code.
