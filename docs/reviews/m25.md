# Review: M25, Atari 8-bit

Branch `m25-atari` (`10a0390` to `3d5f45b`, 11 commits), from `main` at `b080d5d`. Roadmap "M25: Atari 8-bit"; spec 2.1, 12.2; decisions of 2026-11-12 and 2026-11-13.

## Verdict

**Not ready to merge.** Two library bugs must be fixed. One "done when" item is not met: the DLI example has not run on the real OS-B, or on the real XL OS. No OS ROM image is installed in Altirra (question 133), so every Altirra check used AltirraOS, Altirra's own replacement OS. That item needs the developer: either install the ROM images, or have the spec session accept AltirraOS for M25.

`dotnet test` (in `../6502-language-dev`, on `3d5f45b`): 3431 compiler tests and 36 CPU tests pass. No benchmark changed. `SkillTests` pass.

## What changed

- **`--target`** on `tern`, `tern run` and `tern bench`. It is required and may come anywhere in the command. `Platform.All`/`ByName`; `CompileResult.Platform`.
- **Encodings** `atascii` and `atari_screen`. I checked both against the ATASCII and internal-code tables: `$20-$5F` maps to `$00-$3F`, `$00-$1F` to `$40-$5F`, and `$60-$7F` stays. The card suits are right.
- **`Platform.Atari`** follows spec 12.2: `$2000`, `$BC1F`, zero page `$80-$FF`, the four volatile areas, ROM at `$C000-$FFFF`. `Platform.FileOf` writes a `.xex` as `$FFFF`, then one segment per run of bytes, then `RUNAD`. I checked a program with a display list at `$3000`: segments `$2000-$2022`, `$3000-$3007` and `$02E0-$02E1`, with no padding. Zeroed variables are not in the file.
- **`tern run`** keeps per-machine behaviour in `Tools/Machine.cs` (`C64Machine` is the old code moved over). `AtariMachine` has stand-ins for the screen editor through CIOV, and for SETVBV.
- **`lib/atari/atari.tern`**. I checked every register offset (GTIA write and read, POKEY write and read, PIA, ANTIC), every shadow and OS address, and CIOV/SETVBV/SYSVBV/XITVBV against the OS documentation. All are right. SETVBV's arguments (A = 6/7, X high, Y low) and the VBI stubs' pull order (Y, X, A, matching the OS's pushes of A, X, Y) are right.
- **Startup** on the Atari is `cld`, zeroing, then `jsr main` and `jmp halt`. Nothing C64-specific remains.
- **Examples** moved to `examples/c64/`; new `examples/atari/dli.tern` and `hello.tern`. Benchmarks and the generic library modules are checked on both machines.
- **Altirra screenshot script** `tests/tools/altirra-shot.ps1`. I ran `dli.xex` with it on an 800 (48 KB, AltirraOS, NTSC). The rows changed color at each boundary, as the status says.

## Findings

### 1. Must fix: `atari.print(text, 0)` prints a character

`src/lib/atari/atari.tern:160`. `print` puts `n` in ICBLL and calls CIO's put bytes. When the length is 0, CIO prints the byte in A instead of a buffer. `put` relies on exactly that behaviour, and the `tern run` stand-in models it. So a length of 0 prints whatever A holds.

```
import atari
data A = "AB"
fn main() {
    atari.put('X')
    atari.print(addr(A), 0)
    atari.put('Y')
}
```

`tern run --target atari --screen` shows `X#Y`, where `XY` is expected. `c64.print(src, 0)` prints nothing (it is a `for` loop over `0..n`), so the two platforms differ on the edge value. A program that prints a computed length, such as `text.dec8`'s result or the length of an empty string, can hit this.

Fix: return when `n == 0`, and add an `AtariLibraryTests` case that prints 0 characters between two others.

### 2. Must fix: changing an installed VBI handler can jump to half an address

`src/lib/atari/atari.tern:216` (`set_vbi`) and `:229` (`set_vbi_immediate`). Both write the handler's address into `vbi_deferred`/`vbi_immediate` with `stx` then `sty`, and only then call SETVBV. The first call is safe, because the vector still points to the OS. On a second call the vector already points to `deferred_entry`. A vertical blank NMI between the `stx` and the `sty` runs `jmp (vbi_deferred)` with the new low byte and the old high byte. That jumps into the middle of nowhere.

Failing case: a game that calls `atari.set_vbi(addr(title_frame))` on the title screen and later `atari.set_vbi(addr(game_frame))`. The window is 4 cycles per change, so it crashes rarely and is hard to reproduce. The C64's `set_kernal_irq` avoids the same problem with `php`/`sei` ("Interrupts are held off while the vector changes"). An NMI cannot be held off that way. `set_dli` avoids it by turning DLIs off in NMIEN first. SETVBV itself syncs to WSYNC for the same reason.

Fix: before writing the address, point the vector back at the OS through SETVBV: `XITVBV` for the deferred vector, `SYSVBV` for the immediate one. Then write the address, then point the vector at the stub. Or write the two bytes inside the same WSYNC-synced window SETVBV uses. Add a test that installs a second handler while an NMI is due.

### 3. Must fix (done when): no check on the real OS-B or the real XL OS

The roadmap says: "an example with a display list and a DLI color change runs in an Atari emulator (Altirra), on an 800 with OS-B and 48 KB and on an 800XL". Spec 12.2 promises "the 800's OS (revision A or B) or the XL/XE OS". The checks used `/kernel:default`, which is AltirraOS (the window title reads "800 ATOS"), on both machines. I repeated the 800 check and got the same result.

AltirraOS follows the documented entry points closely, but it is not the ROM the spec promises. The two points this milestone depends on are both inside the OS's NMI code: the VBI's push order, and the DLI's bare `jmp (VDSLST)`. `C:\Altirra` has no ROM images, and `Altirra.ini` has an empty kernel path. The comment in `examples/atari/dli.tern:6` gives `/kernel:osb`, which fails on this machine for that reason (question 133).

To meet this item: the developer registers the OS-B and XL OS ROM images in Altirra (Configure System, Firmware). Then the coding session reruns `dli.xex` and `hello.xex` with `/kernel:osb` on an 800 and with the XL kernel on an 800XL. If the developer prefers not to, the spec session can change the roadmap item to AltirraOS. In either case the decision belongs in `docs/decisions.md` or the roadmap, not here.

### 4. Suggestion: `display_list` accepts 0 rows

`src/lib/atari/atari.tern:302`. `atari.display_list(atari.MODE_TEXT, 0, $3400, LIST, 0)` compiles to `70 70 70 41 00 30 00 00`. That is a list with no screen and two stray zero bytes after the JVB. Add `assert rows >= 1`.

An optional second assert: that 24 + rows × scan lines per row stays within 240. A list longer than the screen rolls, and ANTIC's line counts per mode are already a table in `row_bytes`.

### 5. Suggestion: the report's "Code and data" line counts the gaps on the Atari

`src/Tern.Compiler/TernCompiler.cs:393`. For the program in finding 4 the report says "Code and data: $2000-$3007 (4104 bytes)". The `.xex` holds only 43 bytes of program, because it has no padding. On the Atari, give the segments, or the bytes in the file.

### 6. Suggestion: the C64 image is built twice

`Platform.FileOf` builds the `.prg` image from the segments. `TernCompiler.Compile` (lines 264-267) has already built the same `image` from the same segments with the same first address. For a `.prg`, `FileOf` could take that image and prepend the address. Behaviour would not change.

### 7. Note: `--target` given twice

`tern --target c64 --target atari x.tern` builds for the Atari with no message. A second `--target` could be a usage error. This is minor.

Every new piece has emulator tests: encodings (`DataTests`), the `.xex` format with segments, binaries and overlays (`AtariTests`), the run stand-ins including CIO with length 0 (`AtariRunTests`), and the library, with DLIs and both VBIs driven through a stand-in NMI entry (`AtariLibraryTests`). Missing: `print` with 0 characters (finding 1), and replacing an installed VBI handler (finding 2).
