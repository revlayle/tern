## Part 1 (compiler, tools and two small features)

Reviewed at `5f66b29`, 2026-11-08 (commits `5214e10` to `5f66b29`).

**Not ready to merge.** Three must-fix findings, all in the new tools and small to fix. The language features (`using overflow`, `cpu`, `indexed match`, questions 65-67) are correct and well tested. 1850 compiler tests and 36 CPU tests pass. Benchmarks: 1259 / 351130 -> 1254 / 350780 (only `interp`, which lost its range check, as the roadmap expected).

What I checked beyond the tests, by compiling and running small programs:

- `indexed match` on an `i8` with a lowest value of -4: `lda s / sec / sbc #$FC / tax / lda hi,x / pha / lda lo,x / pha / rts`, as spec 11 (no `eor #$80`, question 70). Values in a gap of the span go to the end of the match, and the code after it does not assume A holds the arm's value (`t[i] = r` after a gap gives the right result).
- The two errors of `indexed match` (no pattern besides `_`; X and Y both held by `using` loops).
- `using overflow`: the errors on a plain `fn` and an `inline fn`, as a parameter, as a fixed input (`true using overflow`), and on a `u8` return. `while cpu.overflow()` after `bit hw`, with the body ending in `asm { bit hw }`, is `jmp test` / ... / `bvs loop`. `r = cpu.overflow() as u8` after `adc` is `bvc / lda #1 / bne / lda #0 / sta r`.
- The optimizer never removes or moves an instruction that sets V: its flag tracking covers only N and Z, and the only defined reads of V come right after an `asm` block, which it does not change. `Invert` and `IsBranch` already handle `bvc`/`bvs`. There are no tail calls (`jsr f / rts` to `jmp f`), so the run tool's per-function cycles (by `jsr` and the stack pointer) are complete.
- `tern run --profile` and `.lines` on `sieve`: the per-line rows add up, and main's 8476 cycles match the function table.
- `tern --json` on several errors. The suggestion split works where a message has a fix sentence; many older messages have none, so `suggestion` is often null (question 69).
- `--irq` goes through `$FFFE`, which matches the library's `c64.kernal_off()` / `c64.set_irq()`.

### Findings

1. **Must fix: code after an inlined call is put on the inline function's line in the source map** (`CodeGen.GenInline`, `src/Tern.Compiler/Backend/CodeGen.cs:394`).
   - `GenInline` resets `_lastSource` after the body but does not emit the caller's line again. Everything the caller's statement generates after the inline body is therefore given the last source line of the inline function, which may be in another file.
   - Failing case:
     ```
     var a: [u8; 4]
     var k: u8 = 2
     inline fn g() -> u8 { return k + 1 }
     fn main() {
         for i in 0..4 {
             a[i] = g()
         }
     }
     ```
     `ldx main.i` / `sta a,x` come after `g.inline_end`. The listing has no line 6 comment after them, and `.lines` gives line 3 (`inline fn g() ...`) 10 bytes and has no row for line 6.
   - Same with the `cpu` module: in `while cpu.overflow() { ... }` the `bvs` is counted on `cpu.tern:19`, and so are all five instructions of `r = cpu.overflow() as u8`. Every `if cpu.carry()` in a program puts its branch on the library's line.
   - Why it matters: the roadmap says this map is what M20's index check uses to name the source line of a bad `a[i]`. With this bug, `a[i] = g()` would be reported at `g`'s declaration. `tern run --profile` also gives the cycles to the wrong line.
   - Fix: remember the caller's current source line before the body, and after `Place(end)` emit it again (a `SourceLine`, also in the listing). Test in `LineTableTests`: the program above has a row for line 6 with `sta a,x`'s address. Also test `if cpu.carry()`, whose branch should be on the `if` line.

2. **Must fix: `tern bench --code` gives the wrong line for errors when there are no `--decl` lines** (`BenchVariant.Snippet`, `src/Tern.Compiler/Tools/Bench.cs:16-17`).
   - With no declarations, `head` is empty but the source still starts with `"\n"`. So the snippet starts on line 3, while `FirstSnippetLine` is `0 + 2`, and every error is one line too late.
   - Failing case: `tern bench --code "var x: u8 = 1; x = nope"` reports `line 2:20`; the snippet has one line. `--json --code "x = 1"` gives `"line": 2`.
   - An error in a `--decl` line is given as `code 1` with a line of 0 or less (`--decl "var g: u9" --code "g = 1"` gives `"line": -1` in the JSON, and no line in the text). It should name the declaration, e.g. file `decl`, line 1 of the `--decl` text.
   - Fix: build the source without the leading newline when there are no declarations (or count the lines from the actual text), and map lines before the snippet to the declarations. Tests: an error in a snippet with no `--decl`, and an error in a `--decl`. The current test (`An_error_in_a_snippet_is_placed_in_the_snippet`) has a declaration, so it passes by luck.

3. **Must fix: `--dump` can crash `tern run` with an unhandled exception** (`MemoryDump.Parse`, `src/Tern.Compiler/Tools/RunReport.cs:22` and `:40`).
   - `--dump ""` (or `--dump ":4"`, whose name part is not split off since the colon is at index 0) reads `what[0]` of an empty or wrong string: `IndexOutOfRangeException`, with a stack trace.
   - A variable with a byte count is not checked against the end of memory, as the address form is: with `var w: u8 @ $FFF0`, `--dump w:100` passes the parser and then throws `ArgumentOutOfRangeException` in `RunReport.Text` (also in `Bench.Measure` and the JSON).
   - An agent that gets a stack trace cannot tell what it did wrong. Fix: an empty name is a `FormatException` ("--dump needs a variable or an address"); the variable form checks `Address + size <= $10000` as the address form does. Tests in `RunToolTests.A_bad_dump_says_what_is_wrong`.

4. **Suggestion: an `indexed match` on a value already in X can index with X directly** (`CodeGen.GenMatch`, `CodeGen.cs:667`).
   - `for i in 0..4 { indexed match i { 0 => ... 1 => ... } }` (counter in X) gives `txa / tay / lda hi,y / pha / lda lo,y / pha / rts`.
   - When the value is a variable held in X or Y and there is no `sbc`, `lda hi,x` / `lda lo,x` would do, 4 cycles and 2 bytes less. This matches spec 11 as written, so it is not required. It could go to M20 or later.

5. **Suggestion: say in `tern run --help` that overlays are not loaded.** The runner loads only the program file. A call into an overlay stops at a `brk` ("often a jump into empty memory"), which is right but does not say why. One line in the help and the `Runner` summary would do.

6. **Suggestion: the per-line profile adds cycles by address** (`Profile.CyclesOf`, `LineTable.cs`). Two overlays in one area share addresses, so a run that loads them (not possible today, see 5) would count each one's cycles on both. Nothing to change now; worth a note for when the runner loads overlays.
