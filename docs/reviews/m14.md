## Review (`b2eb5ba`), 2026-11-07

**Not ready to merge: two must-fix items.** Both come from how a real 1541 behaves. The fake KERNAL in `IoTests` does not model either, and the example does not exercise them. 1371 tests pass (36 CPU, 1335 compiler). `BenchmarkTests` is unchanged. Unused `io` functions cost nothing, and an unused `save` uses no zero page (`save_from` is not allocated). Code shapes are as expected: KERNAL calls are a direct `jsr`, `write`'s loop is a `using Y` loop around `jsr $FFD2`, and `readst() & ST_NO_DEVICE != 0` compiles to `and #$80`.

I checked in VICE (`x64sc -drive8truedrive`, a fresh `.d64` per run) with three probe programs on top of the example. Results:

| Probe | True drive | Virtual drive |
|---|---|---|
| write `T` (10 bytes), read it back | 10 bytes, status $40 | same |
| `T` open for reading and `U` open for writing; read `T` to its end, then `write(U)` | write returns false, `U` has 10 bytes | same |
| open `V` for writing, `drive_status(8)`, `write(V, 10)`, read `V` back | **write returns true, `V` has 4 bytes** | write false, 10 bytes |
| same, with channel 15 opened first and kept open while reading the status | write false, 10 bytes | |
| `open` of a missing file, `status()`, `read(…, 40)`, `status()` | **0, 1, $42**, then the channel shows `62, FILE NOT FOUND` | |
| `load` of a missing file | carry set, status $42 | |
| `examples/highscore.tern` | `SAVED`/`LOADED: HIGH SCORE 12340`, `STATUS: 00, OK,00,00` | |

The stale-status concern was unfounded. After `T` hits its end ($40), `write(U)` still returns false.

### 1. Must fix: `drive_status` and `command` close every open file on the drive

`io.tern:126` and `io.tern:145`: both functions end with `close(15)`. On a 1541, closing the command channel closes **all** channels on the drive. VICE's true drive emulation, which runs the 1541's own ROM, shows this; its virtual drive does not. The module header (`io.tern:13-15`) and `open`'s comment (`io.tern:81`) tell the user to do exactly this: "after opening … a disk file, call status() or drive_status()".

Failing case (true drive): `io.open(5, 8, 5, "@0:V,S,W")`, then `io.drive_status(8, …)`, then `io.write(5, addr(D), 10)` returns **true**, and the file `V` holds 4 bytes. The same with channel 15 kept open gives false and 10 bytes. `command()` has the same effect, e.g. a scratch sent while a file is open.

Fix suggestion (the coding session's choice): the usual idiom is to open channel 15 once, before the data files, and close it last. For example, `open_command(device) -> bool` / `close_command()` (or `command` without the close), with `drive_status` reading from the open channel and not closing it. A one-shot form may stay for use when no file is open, if its comment says it closes all files on the drive. Update the module header to match. Tests: the fake drive should drop its other open files when channel 15 is closed, so a test of the documented sequence (open a file, read the status, write) fails today and passes after the fix.

### 2. Must fix: a missing file is not in `status()` after `open`, and `read` counts a byte it did not read

- `io.tern:81` ("a missing file shows in status() or drive_status()") and the fake's OPEN (`IoTests.cs:55`, status $02 for a missing file) are wrong for a real drive: after `open` of a missing file, `status()` is **0**. The error shows up at the first byte read (status $42: end of file + read timeout) and on the command channel (`62, FILE NOT FOUND`). `A_missing_file_shows_in_the_status_and_not_in_the_carry` (`IoTests.cs:345`) tests the fake's invented behavior.
- `read` (`io.tern:90-96`) stores and counts the byte before it looks at the status. On a missing file it returns **1** with a junk byte in `dst[0]`. The comment says it "Returns how many bytes were read". With status $42 no byte was read; only with $40 alone is the last byte valid. Fix: after `chrin()`, if `readst() & ST_TIMEOUT != 0`, stop without counting; for $40, count and stop, as now. `Read_stops_on_an_error_status` (`IoTests.cs:333`) asserts the current behavior (`n == 1`, "the first byte, then the error") and needs to change with it.
- `io.tern:13-15` says a drive reports "file not found" only through the status and the command channel. For `load` that is wrong: LOAD of a missing file sets the carry (VICE: `io.load` returned true, status $42). Say which functions see it in the carry (`load`) and which do not (`open`, `save` of a full disk).

### 3. Suggestion: `save` with `last = $FFFF` saves nothing

`io.tern:69-72` passes `last + 1`, which wraps to `$0000` for `$FFFF`. The KERNAL's SAVE loop compares the pointer with the end before writing each byte (`$FCD1`), so an end of `$0000` stops at once. The file gets only its two address bytes. `Save_to_the_last_byte_of_memory_wraps_the_end_address_to_zero` (`IoTests.cs:172`) and `status.md` ("also at `$FFFF`") present this as working. It is a KERNAL limit; say in `save`'s comment that `last` must be below `$FFFF`, and drop or reword the test.

### 4. Suggestion: `drive_status` and `command` close channel 15 even when OPEN failed

`io.tern:124-126`, `io.tern:135-145`: if OPEN fails because logical file 15 is already open (KERNAL error 2, carry set), the function still calls `close(15)` and closes the caller's file. Once finding 1 is fixed, a program that keeps channel 15 open is the normal case. Close only when the open succeeded.

### 5. Suggestion: `c64.load` grew from 24 to 33 bytes

`c64.tern:52`: `return io.kernal_load(0)` loads a dummy address (`ldx #0 / ldy #0`, 4 bytes) and returns the carry as `bcs t / clc / rts / t: sec / rts` (5 bytes more than an `rts` after the `jsr`). The old `asm fn` was 24 bytes; the new one is 33. Two options: a second fixed-address declaration without the address (`fn kernal_load_own(0 using A) -> bool using carry @ $FFD5`), and, in the code generator, compiling `return f()` of a `bool using carry` routine to `jsr f / rts` (spec 7: "evaluates the condition straight into the carry where possible"). That shape also affects `io.load` and `io.open`. The code generator part is for the M17 list, not this milestone. Also, `c64.load`'s comment says "about 40 bytes" per call; the call site is 19 bytes plus the shared 33.
