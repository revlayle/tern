# Review: M26, Apple II

Branch `m26-apple2` (`5e7a55a` to `6614097`, 8 commits), from `main` at `94532f4`. Roadmap "M26: Apple II"; spec 2.1, 10.1, 12.2, 13; decision 2026-11-13 (the Apple II platform) and questions 138, 139.

## Verdict

**Not ready to merge.** Three things must be fixed, all small: an ordinary program can fail to compile because the compiler's own zero-page placement crosses from `$FF` to `$00`; one new compile error has no test; and the example's build outputs are committed. Every "done when" item is met. I ran the hi-res example in AppleWin on both machines myself.

`dotnet test` (in `../6502-language-dev`, on `6614097`): 3544 compiler tests and 36 CPU tests pass. No benchmark changed. `SkillTests` pass.

## What changed

- **Label writers** (`LabelFormat`): `Vice`, `Mads` and `AppleWin`, named by `Platform.Labels`. The driver no longer works out the format from the output type (question 138). C64 and Atari output is unchanged.
- **`Platform.Apple2`** follows spec 12.2: `$2000`, `$BEFF`, zero page `$50-$FF` then `$00-$1F`, volatile `$C000-$CFFF`, encoding `apple2`, `.system` output. Overlays and binaries are `.bin` (question 141).
- **System file and startup** (`TernCompiler.Apple2.cs`). I read the copy code for both directions and checked the order rule. The copies use only relative branches until `jmp moved`. A move up copies from the top; the remainder after the whole pages is copied first. The order loop rejects a copy that would land on the copier or on a source not yet copied. I ran a program with three 256-byte tables moved down to `$0800` (an exact page multiple, so the remainder is 0). The sums were right. The reset vector, power-up byte (`EOR #$A5`), Ctrl-U, SETNORM, INIT, SETVID, SETKBD, HOME, CLOSE (count 1, reference 0) and QUIT (count 4) are correct.
- **`tern run`** (`Apple2Machine`): checked against the monitor's COUT1/VIDOUT. Codes from `$A0` are masked with INVFLG. Codes below `$80` are stored as they are. Of `$80-$9F`, only return, line feed and backspace act. Lines wrap at WNDWDTH. `tern bench --target apple2` works.
- **`lib/apple2`**: I checked the ROM entry points (COUT `$FDED`, HOME `$FC58`, PRBYTE `$FDDA`, RDKEY `$FD0C`, BELL `$FF3A`, WAIT `$FCA8`) and the zero-page and soft-switch addresses. The text and hi-res row formulas are right. `plot`'s x ≥ 256 path (`+4`, column 36) is correct up to x = 279. `mli` writes the command and address into the 3 bytes after its `jsr $BF00`.
- **`text_digits`** has `ZERO`, `MINUS` and `POINT`. `text`, `wide`, `bcd` and `float` take their codes from it (question 145).

## Findings

### 1. Must fix: the compiler's own zero-page choice can cross the `$FF`/`$00` gap

`src/Tern.Compiler/Backend/Allocator.cs:105` (best-effort candidates) and `:114` (`ZeroPageAddress`). The best-effort step adds a variable to zero page whenever the *total* still fits in 208 bytes. It does not check whether the variable can sit within one range. On the Apple II the bytes are `$50-$FF`, then `$00-$1F`, so a 2-byte variable can land on `$FF`/`$00`. Placement then fails with an error the program cannot reasonably fix. The program has no `@ zp`, and "Join the ranges" is impossible on the platform's own map:

```
var b0: u8
...                 // b1 to b174, 175 u8 globals in all, each used once in main
var w: u16
fn main() { b0 += 1 ... b174 += 1; w += 1 }
```

`tern --target apple2` gives: `'w' (2 bytes) would cross the end of a zero-page range at $00. Zero-page ranges: $50-$FF, $00-$1F. Join the ranges or reorder the variables`.

Question 140 accepts this error after 176 bytes, but only for variables the program *requires* in zero page. For best-effort variables the compiler is free to put the variable in RAM instead, or to skip a byte, so a valid program must not fail. Frame variables are placed the same way after the globals (`:136`) and can hit the same gap. Fix: keep a best-effort variable out of zero page when its address would cross a range end. Add a test with the program above, and one for a frame variable.

### 2. Must fix: the "every order of the copies" error has no test

`src/Tern.Compiler/TernCompiler.Apple2.cs:217`. The coding conventions require a test for every new compile error. The status says "both copy errors" are tested, but `Apple2Tests` covers only the copier-overlap error (`An_area_over_the_running_copier_is_an_error`). The second error is reachable:

```
memory {
    $8000..=$BEFF program
    $2400..=$7FFF program
}
data T0: [u8; 256] = repeat(0, 256)
...                 // T1 to T99
var n: u8
fn main() { n += T0[1] ... n += T99[1] }
```

This program gives `... every order of the copies overwrites bytes of the file before they are copied (the area at $8000-$BEE0 first). Start the first program area at $2000, or place the areas further from $2000-$85E0`. The start area's copy to `$8000` lands on the second area's source, and the second area's copy to `$2400` lands on the start area's source.

### 3. Must fix: the example's build outputs are committed

`examples/apple2/hello.{lines,lst,sym,system}` and `hires.{lines,lst,sym,system}` are checked in (`2a9b038`). `.gitignore` ignores the build outputs of `examples/c64` and `examples/atari`, but has no lines for `examples/apple2`. The files will go stale with the next compiler change. Remove them and add `examples/apple2/*.system`, `*.sym`, `*.bin`, `*.lst` and `*.lines` to `.gitignore`.

### 4. Suggestion: the CLI help splits its list of output files

`src/Tern.Compiler/Tools/Cli.cs:26`. The new paragraph about the Atari's and the Apple II's files sits between the `.vs` line and the `.lines` line. `tern --help` now prints `<output>.lines` after the paragraph, cut off from the rest of the list. Move the paragraph below the list.

### 5. Suggestion: the copier tests constants at run time

`TernCompiler.Apple2.cs:91-93`, `:103-104`, `:114-115`, `:122-123`. `ldx #pages` / `beq` and `ldy #rest` / `beq` test values the compiler already knows. Emit only the loops a copy needs, and drop the `beq`. That saves 2-4 bytes per moved area, plus a whole loop when the pages or the remainder are 0. Question 144's "47 or 48 bytes per moved run" would change.

### 6. Suggestion: the system file's errors point at `fn main`

`TernCompiler.cs:270` passes `program.Main.Pos` to `SystemFile`. In the case in finding 2, the error is on line 106 (`fn main`), but the cause is the memory block. The memory block line that placed the blocked area, or the block itself, would lead the reader to the fix.

### 7. Suggestion: `lib/text_digits.tern`'s comment names only the Atari's replacement

Line 3 says "(lib/atari/text_digits.tern: ATASCII)". Add `lib/apple2/text_digits.tern`, as `text.tern`'s header already does.

### Notes on the status questions

Questions 140-147 are for the spec session. Question 140 interacts with finding 1: whatever order the spec settles, best-effort placement must not produce the error. Question 142: the Ctrl-U path did not run in AppleWin. The code is right for the firmware's hook, but no test or check covers it. Question 147's new float cycles follow from the code moving and are reflected in `FloatTests`.

## Tests

Good coverage: the memory map, zero-page order, the file and startup code (read from the listing), copies in both directions, the overlapping move up (`dec $51` in the listing), fixed data in a gap, the size error, the CLI's files, `tern run`'s COUT (row order, wrap, scroll, INVFLG, control codes), the MLI stand-ins, every library function, and the benchmarks with the same results. Missing: the second copy error (finding 2), and a zero-page placement across the gap (finding 1).
