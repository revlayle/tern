## Findings

### 1. Suggestion, with a question for the spec session: `tern run` now reads seeded bytes at I/O addresses and at OS variables the ROM sets

`Runner.Run` calls `StartState.Fill(ram)` over all 64 KB before `machine.Start`. `Start` sets only the screen, the cursor and a few vectors. So the I/O space and OS variables that the ROM initializes now read fixed pseudo-random bytes in `tern run`. They used to read 0. Some of these bytes look like input:

```tern
// apple2: waits for a key
var key: u8 @ $C000
var got: u8
fn main() {
    while key < 128 { }
    got = key
}
```

On `main`, `tern run --target apple2` waits until the cycle limit (no key). On the branch, main returns at once with `got = $C6`, a key that was never pressed. On the C64, `$DC00` (joystick port 2) reads `$97`, which is "right" held, and `$D012` reads `$18`. The `sprite.md` run of `game.tern` shows this as its `A` changing from `$00` to `$18`. On `main`, `$DC00 = 0` was also wrong ("everything pressed"), so this is not simply a regression. But question 171's decision talks about memory the program never wrote, and its reason is to catch reads of uninitialized RAM. Input registers and OS variables are a different case: on the machine they hold "no input" or the ROM's value.

Question for the spec session: should each machine's `Start` set the idle values that the ROM and hardware give? For example `$C000 < $80` on the Apple II, `$DC00`/`$DC01 = $FF` on the C64, and `CH ($2FC) = $FF` on the Atari. Or is `--set` the intended way to give these values? If idle values are wanted, they belong in each `Machine.Start`, next to the screen, so R4's "one description" holds.

### 2. Suggestion: a few instruction facts are still written by hand

The done-when ("no list of instruction effects ... exists twice") is met for the analyses. These small lists remain, and the table already holds each fact:

- `CodeGen.cs:435` (`GenInterrupt`): `i.Mnemonic is Adc or Sbc or Jsr` means "reads D, or calls". The table could give it as `Effects(...).Reads.HasFlag(CpuState.D) || Flow == Flow.Call`. This matters most in M29, when the 65C02 and the 2A03's `cld` decision arrive.
- `CodeGen.cs:237` (`AHolds`): `Jsr or Brk` is the optimizer's `ChangesAnything`.
- `CodeGen.cs:198` (`Rts or Rti or Jmp`) and `CodeGen.cs:160` (`EndsWithJump`, `Rts or Jmp`) are `!Instructions.FallsThrough`. Note that the two lists differ: `EndsWithJump` leaves out `rti`.
- `Checker.Bodies.cs:25` (`Rts or Rti` in an inline asm fn) is `Flow is Return or ReturnFromInterrupt`.

None of these changes behavior today. R7 will search for exactly this kind of list.

### Notes (no change needed)

- `Checker.Asm.cs:309` now records `JumpVectorOffsets` only when the set has the page wrap. That is right, since the offsets exist only to avoid `$xxFF`. A future variant without the wrap will also skip the "Move 'v'" error, as intended.
- `DeadAtReturn` computes `Positions` and `RegistersLive` again for each candidate load in a function with a jump table. This is quadratic only in such functions, and the suite time is unchanged (about 10 s). If a large `indexed match` function ever compiles slowly, cache the liveness per pass.
- The costs.md bench now compares `$C000` with itself, so that the seeded memory does not end the loop early. The program column moved by 2 bytes (85 → 83, 99 → 97) because the constant changed, not the code generator. The cycles are the same.
