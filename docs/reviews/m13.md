### 2. Must fix: an inline function of another overlay in the same area can read that overlay's variables

`Checker.cs:1631` leaves inline callees out of the same-area call check (`!callee.IsInline`). That part is right, because an inline body is copied into the caller. But the copied body can still use the other module's variables. `UseGlobal` (`Checker.cs:264`) checks them only against the function being checked, which is the inline function in its own module, so no error is given:

```
// l1.tern (overlay)
import l2
fn go() -> u8 using A { return l2.peek() }

// l2.tern (overlay, same area)
var lives: u8 = 3
inline fn peek() -> u8 using A { return lives }
fn run() { lives += 1 }

// main.tern
import l1 @ levels
import l2 @ levels
memory {
    $0801..=$5FFF  program
    $6000..=$6FFF  overlay levels
}
var r: u8
fn main() { r = l1.go()
 l2.run() }
```

This compiles. `l1.go` at `$6000` does `lda l2.lives` (`$6004`). That address is past the end of `l1.prg` (4 bytes), so while `l1` is loaded, `go` reads whatever is left in memory there. This is the same bug that the "uses another overlay's variable" error (decision 56, provisional) exists to prevent. Fix: when an inline callee comes from another module in the same area, apply the variable check to the globals the inline body uses, or reject the call. Add a test.

### 3. Must fix: a fixed-address `var` may overlap an overlay's code without an error

`CheckFixedAddresses` (`TernCompiler.cs:300-325`) checks fixed variables against `code.Areas` (resident program areas), region use and fixed data. It does not check them against overlay sections. This compiles, and `x = 1` writes into `l2`'s code:

```
import l2 @ levels
memory {
    $0801..=$5FFF  program
    $6000..=$6FFF  overlay levels
}
var x: u8 @ $6001
fn main() { x = 1
 l2.run() }
```

For resident code the same overlap is an error ("overlaps the program and its variables"). Do the same check against each overlay file's range, and add a test.

### 4. Suggestion: point the "overlay does not fit" error at the import

`Assembler.cs:177` reports the error at `1:1` of the main file. The `import level1 @ levels` line is a more useful place. The assembler does not know source positions, so the error may need to be caught in `TernCompiler` and given `ImportDecl.Pos`.

### 5. Suggestion: `data x @ $addr` in an overlay module

`data T: [u8; 2] @ $6800 = [1, 2]` in an overlay module whose area is `$6000-$6FFF` gives "not in a program or reserved area... Add a 'reserved' line". If the user does that, the data goes into the main program file, not the overlay's file. Spec 8.5 says the overlay file holds the module's `data`. Either put fixed data that lies inside the module's own area into its file, or give a message that says why it is not allowed. Either way, ask the spec session (new question).
