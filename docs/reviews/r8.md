## Findings

### 1. The cartridge alignment test does not check the padding it was written for (suggestion)

`tests/Tern.Compiler.Tests/Declarations/AlignTests.cs:164-167`. The bug was the report's padding count for an aligned `var` with an initial value on a cartridge. The test reads the number from the report line, then checks the line against a text built from that same number, and checks only that it is 0 to 255. Any wrong count passes: a block taken from the wrong list that gives 37 bytes would still pass. The test does guard the crash, which threw before the fix. The program places `level` at `$0200`, the start of RAM after the stack, so the right count is 0 (the CLI reports "0 bytes of padding before it"). Fix: `Assert.Equal($"Aligned level: ${at:X4} (@ align(256)), 0 bytes of padding before it", line)`, or work out the padding from the addresses below `level`, as the C64 test at line 93 does from the listing's "left free" note.

### 2. Marking whole theories filters out 126 cases that pass on every target (suggestion)

Step 3 marks a theory as a C64 test when any of its rows failed (the status says so). With `--filter "Platform!=c64"`, 126 cases that pass on the Atari, the Apple II and the NES no longer run there: 59 rows of `AsmTests.Reports_errors`, 20 of `DataTests.Reports_errors`, 12 of `BinaryTests.Reports_errors`, 9 of `DataTests.Underscore_length_errors`, 8 of `VolatileTests.Reports_errors`, 7 of `MemoryTests.Reports_errors`, and a few library rows. Most are whole-message error tests, the checks that guard M28's message split on every platform. The roadmap only asks to mark tests, so this meets R8. Fix, now or with the after-release rewrite to `TestTarget` addresses: split each such theory into a portable theory and a marked one (`Reports_errors` and `Reports_c64_errors`), moving the rows by the trx logs as step 3's script already groups them.

### 3. `--dump` errors: a glued prefix and no help pointer (suggestion)

`src/Tern.Compiler/Tools/Cli.Commands.cs:81` puts "--dump " in front of `MemoryDump.Parse`'s message. For the messages that start with the value (`--dump 'x:0' shows no bytes.`) that reads well. For `RunReport.cs:38` it gives `--dump No variable 'nosuch'. Write a local as 'function.name'`, which reads as broken text (tested so in `CliTests.cs:56`). Also, `--set`'s errors end with "Run 'tern --help' for the options" and `--dump`'s do not, though both are value errors of `tern run` options. Fix: make the message `No variable 'nosuch' for --dump`, or have the prefix read `--dump: `, and give both the same ending.

### 4. Two option help texts still name each platform by hand (suggestion)

Suggestion 3 is done as the roadmap lists its parts (the cartridge messages, the run-model paragraph, `ProDosSystem`). But `Cli.Options.cs:42-43` (`--target`: "c64 (Commodore 64), atari (Atari 8-bit with 48 KB or more), ...") and `:64` (`--screen`: "$0400 on the C64 and the Apple II, SAVMSC on the Atari; on the NES ...") are shared code that a new platform has to edit, which is the aim suggestion 3 finishes. Fix: build them from `Platform.All` (a one-line description per platform, as `Title`; the screen from each `Machine`, as `IdleInput`). Small; may go with the X16 or C128 work, where it is first needed.

### 5. The help's brk sentence now covers undocumented opcodes too (suggestion)

`Cli.cs:164`: "A brk stops the run, and so does an undocumented opcode, unless a machine below says otherwise." On `main`, the exception named the brk only, and the opcode sentence had none. No machine makes an exception for undocumented opcodes, so the new sentence promises a possible exception that no machine gives. Fix: "An undocumented opcode stops the run. A brk does too, unless a machine below says otherwise."

### 6. `Library` adds a third copy of the stand-in step (suggestion, for the accepted item)

`tests/Tern.Compiler.Tests/Harness/Library.cs:78-88` copies the stand-in call and its `rts` (pull the return address, `PC = address + 1`) that `Run` and `Runner` already have. The rest of review R6's suggestion 4 (one step loop for `Run` and `Runner`) is accepted for after the release (decision 2026-11-21). `Library` now belongs on that list too, so the shared loop covers all three. `Library` also calls `Machine.Start` only where the startup calls the ROM (line 30), so library tests on the C64 and the Atari start without idle input. No library routine reads input, so nothing fails today. Fix: name `Library` in the accepted item (roadmap or status); no change for R8.
