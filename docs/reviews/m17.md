### Findings

#### 1. Suggestion: F21's text says 4 bytes, but its row says 5

F21 says it "saves 5 cycles and 4 bytes a call". The calls row and item 19 give 903 / 5. On average it saves 4.5 cycles a call (4 on the false path, 5 on the true one). Return the carry directly and only one `rts` remains, so the `bcc`, `clc`, `rts` and `sec` go: 2 + 1 + 1 + 1 = 5 bytes. Change the F21 text to 5 bytes.

So an F21 that also handles `>` and `<=` would recover about 500 of the 903 cycles from the source as written. The rest would still need the rewrite. Nothing to change before merging, but worth a line in F21 when M18 is scoped.

### Findings

#### 1. Suggestion: the 17,616 cycles of F18 are optimizer work, but appear only as item 17

**What the report does.** The "2 after F1 + F2" column (23,094) is split into 5,478 for the rewrite and 17,616 for F18. F18 keeps the swapped element in a register and uses the A that the compare left, and the report itself calls it "class 1 on the rewritten source". In section 7, though, F18 is not a class 1 item. It is folded into item 17, which is class 2. A spec session that schedules M18 from the class 1 items would not see what would be the fourth-largest optimizer change.

**The original source can get the same code.** Look at `bubble.tern` as written:

```
var a = values[i]; var b = values[i + 1]; if a > b { values[i] = b; values[i + 1] = a }
```

`values[i]` is not written between the read of `a` and the first store, so the compare can use it directly. `a` is needed only for the swap, so it can be loaded into Y just before `values[i]` is overwritten. With F2 and F3, that gives the assembly's inner loop exactly:

```
lda values+1,x / cmp values,x / bcs / ldy values,x / sta values,x / tya / sta values+1,x
```

That is 16 cycles a swap, the same as `ldx / sta / txa / sta`. So the whole 23,094 is reachable as class 1, with no rewrite at all.

**Suggestion.** List F18 in section 7 as a class 1 item with its 17,616. In item 17, say that the optimizer could give the same code from the original form. Then the spec session can decide whether the guide should ever recommend `bubble.direct`.

#### 2. Suggestion: the bit test in `fib16`'s `mul` is class 4 in the table and class 1 in the text

**The inconsistency.**
- The fib16 table puts the `lda b / and #1 / beq` bit test (50 cycles, 4 bytes) in class 4 "for the reasons in section 4". The `math.mul16` library row calls its bit test class 4 too.
- Section 4's second bullet says the opposite: moving `b = b >> 1` before the `if` and branching on the carry "is class 1 in principle". It is a reordering within one function, with no change to the source or the language, which is the roadmap's definition of class 1.

**Suggestion.** Move the 50 cycles and 4 bytes to class 1, unranked or as a small F item. Alternatively, say why a reordering the report calls possible still counts as assembly-only. The totals hardly change.

#### 3. Suggestion: the `calls` class 2 cell is not measured, but section 1 says it is

Section 1 says of class 2 "now" that "each part is measured by a variant". The method paragraph and the calls section say otherwise, and they are right: the `calls` cell (2,103 cycles / 9 bytes, for making `bigger` an `inline fn`) is counted, not measured. `calls.inline` inlines all three functions and measures −7,899.

**Suggestion.** Fix the sentence. Or add a `calls.bigger` variant (only `bigger` as `inline fn`) so that the advice in item 16 is backed by a measurement like the others.

#### 4. Suggestion: question 63 could include a second proof that `i + 1` does not wrap

The report's argument is that `for i in 0..last` with `last: u8` gives `i <= 254`. There is a simpler one in `bubble`: the same loop body also reads `values[i]`. Spec 3.2 says an index outside the array "is not supported" and "the compiler may assume it never happens", so `i < 100` and `i + 1 <= 100`. This proof does not depend on the loop's bounds. It also covers `while` loops and the constant-bounds case.

Whether the optimizer may draw conclusions from that assumption, beyond "a[i] = v changes only a", is a spec question. Adding it to question 63 would let the spec session settle both readings at once.

#### 5. Suggestion: status.md still gives the first report's class totals

The M17 entry under "Done" in `docs/status.md` still has the old numbers: "1 optimizer 117,637, 2 how written 43,846, ...". The entry says it was replaced, and the rework entry above it has the new totals. A reader skimming the file may still take the old numbers.

**Suggestion.** Shorten that entry to point at the rework entry.

### Findings

#### 1. Must fix: some cells in the section 1 table are remainders, and some are wrong

The report says "the columns add up to the measured gap". They do, but in several rows only because one cell was computed as gap minus the others. The report should either count these cells or label them as remainders. Recounts from the profiles and the `.asm` files:

- **sieve** (256 cycles, given as class 4, "`n` is in memory where the assembly keeps it in Y ... Nothing to fix"). The profile says something else:
  - 157: `count` is counted in memory (`inc count`, 54 times, 5 cycles), where the assembly counts in X and does `stx count` once. This is F7 (a single-root global kept in a register across a loop), which the report calls class 1.
  - 82: `lda composite,x` crosses a page. `composite` is at `$0852`, and the 254 loads take 1098 cycles, not 1016. The assembly's table is at `$c000`. See finding 5.
  - 10: the `while` loop's entry `jmp` and one extra test.
  - 6: `lda n / asl / tay` where the assembly has `tya / asl / tay`.

  So nearly all of sieve is class 1, and none of it is assembly-only.
- **sum16** (F1 4,800 + F8 2,424 = 7,224 exactly):
  - F8 is 15 cycles an iteration: 62 against 47 for the shift-and-add. Over 200 iterations that is 3,000, not 2,424.
  - An item the report does not mention: after `sta main.v / bcc c3 / inc main.v+1`, line 11 reloads `lda main.v`, although A still holds it on both paths. The assembly stores A directly. That is 600 cycles and 2 bytes, class 1.
  - The sum loop also has layout effects that offset each other. Tern crosses a page in `values,x` and `values+200,x` (+376). The assembly crosses a page in `values+200,x` (+288) and uses absolute addresses for `total` and `largest`.

  The row still adds up to 7,224, but not as F1 + F8.
- **bubble:**
  - The outer loop and the setup cost 1,004 cycles more than the assembly, not 1,193 (F9): 99 × 10 for `ldx #0 / cpx last / bcs` and the `lda #0 / cmp / bcc` test against `dec / bne`, plus 3 in the setup.
  - The class 2 cell is then 23,094, not 22,905. Per iteration that is the 6 cycles of `lda values,x / sta a / cmp a` against `cmp values,y`, less 3 cycles on each swap, where the assembly's `ldx values,y` reload costs more than Tern's `lda main.a`.
- **interp:**
  - Class 4 (249) is a remainder. The `match` range check alone is 369 cycles (`cmp #9` 148 + `bcc/jmp` 221), which the per-benchmark section says.
  - `DEC => stack[sp - 1] -= 1` compiles to `lda / sec / sbc #1 / sta` (13 cycles) where `dec stack-1,x` takes 7. That is 60 cycles of class 1 that is not counted. F10 lists only `a[i] += 1`.
- **crc8:** "small items" (262) is 768 minus 512 plus 6:
  - 768: the outer counter `i` lives in memory (`inc main.i`) because the inner `repeat` took X. The assembly uses Y for the inner loop and X for the outer one, a class 1 register choice.
  - −512: the assembly's `crc` is at `$c000`, an absolute address.
  - 6: setup.

  Write these out.
- **enemies** "335 other small items" and **fib16** (7 cycles) are small enough to stay remainders, but say so.

Fix: recount the rows above. Add an "other / not explained" column, so that a remainder is visible as one instead of going into a class.

#### 2. Must fix: class 2 is described as measured, but half of it is neither measured nor possible today

Section 1 says "Class 2 items are *measured* (a variant)". Section 6 item 9 says "measured … 43,846" and "independent of it and can be written now".

But 22,905 of the 43,846 (52%) is bubble's remainder (finding 1). It can only be reached after F1 and F2: today the rewritten form, `bubble.direct`, is slower (253,936 against 226,948). The measured class 2 savings that a programmer can get today are 20,941:

| benchmark | saving |
|---|--:|
| calls | 5,203 (capped at the gap; the variant itself saves 7,899) |
| copy | 10,174 |
| enemies | 5,004 |
| interp | 560 |

Fix: split class 2 into "measured, available now" and "depends on F1 + F2" in section 1 and in section 6 item 9. In section 6, say which advice the guide can give now.

#### 3. Must fix: the 274-byte gap is not split by class

The roadmap asks for "for each difference: bytes and cycles", and the done-when list asks for class totals that add up to the measured gap. The report gives the byte gap per benchmark and says "Not split by class". Some F items give bytes (F1 about 80, F2 10, F3 2 a store), most do not.

Bytes are static: they can be counted from the listings, without profiles, so this is easier than the cycle table. The byte gap is 22% of Tern's size and is a different picture from the cycles. In `copy` and `interp`, by the report's own words, it is "mostly structure". So the claim that bytes follow cycles "in about the same proportion" needs the numbers.

Fix: add a bytes table with the same columns as the cycle table, and bytes for each F item in section 6.

#### 4. Must fix: register-held values and carry-as-data are put in class 4 without a check against the design rules

The roadmap gives two examples of class 3, *language*: "a value kept in a register across a loop or call, or a carry passed between statements". Each class 3 item is to be "checked against the design rules". The report puts both kinds in class 4 or leaves them unclassified:

- `wide.add32`, `math.mul8` and `math.div8` (section 4: "the carry as data") are called class 4.
- `math.abs16` gets no class.
- sieve's register-held value is called class 4 (see also finding 1).

The conclusion may well be class 4: the carry as a value between statements probably fails rule 1 or rule 3. But then the report should say which rule and why, because this is the class the roadmap asked the spec session to decide on.

Fix: for each library row and for F11, give the class and the design rule that decides it.

#### 5. Suggestion: arrays placed after the code cross pages on indexed loads

Tern puts data right after the code, so an `abs,x` load can cross a page (+1 cycle each). The assembly versions put their tables at `$c000`.

| benchmark | load | cost |
|---|---|---|
| enemies | `lda enemies+48,x` (table at `$08F5`) | 3,450 cycles where it would be 3,200: +250 |
| sieve | `lda composite,x` | +82 |
| sum16 | `lda values,x`, `lda values+200,x` | +376 (the assembly loses 288 the same way) |

That is about 700 cycles over the nine benchmarks, and none of it is in the report. The fix is class 1, in the allocator: place an indexed array so that its indexed range does not cross a page when there is room. Add it to F10 or the ranked list.

#### 6. Suggestion: question (b) is already answered by the spec

Section 6(b) says that keeping a single-root global in a register "is not written in spec 7 or 11". The spec already says it:

- Spec 4, volatile memory: "All other memory is ordinary: its values may be kept in registers, and redundant reads and writes removed."
- Spec 8.1: "A global variable used from two roots is volatile."

So F7 needs no new rule. Drop the question, or ask only whether the spec should give an example.

#### 7. Suggestion: describe F2 against what decision 42 already allows

Decision 42 already permits folding "a sum it can prove does not wrap (a loop counter with constant bounds)". Bubble's loop is `for i in 0..last` with a variable `last: u8`, so F2 goes beyond that example: there, `i <= 254` because `i < last <= 255`.

Question (a) should say this, and say whether the constant-bounds case (`for i in 0..N { a[i + 1] }`) is folded today. Going by F2's title, it is not, though the decision allows it.

#### 8. Suggestion: no library routine from `text` or `sprites`

The roadmap names five modules: `math`, `wide`, `bcd`, `text` and `sprites`. The six routines come from the first three. `sprites.raster` is the hottest real code in the library, and a routine from it would test whether the findings hold outside small benchmarks. Add one, or say why none was picked.

#### 9. Suggestion: the llvm-mos flags differ from the roadmap

The roadmap says `-Os`, and the code uses `-Os -fno-lto`. The reason is stated in `comparison.md`: LTO would remove the result variables that only the test reads. That is reasonable. Mention it in status.md for the spec session, since it can affect llvm-mos's numbers (`calls`, `fib16`).
