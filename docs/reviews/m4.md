### A. Suggestion: `x.foo()` on a declared variable says `x` is not declared

`Checker.cs:1052` (the call path) and `NotDeclared` (`Checker.cs:102`). Since the parser now joins `name.member(` for any name, `var x: u8` / `x.foo()` gives `'x' is not declared. To use the module x, add 'import x' at the top of the file`. That is wrong: `x` is declared. (`x = x.foo`, without the call, correctly gives `Unknown member '.foo'`.) Before the fix it was a parse error. Rare now, but more likely once structs arrive in M5 (`v.field()`). Fix: in `NotDeclared`, give the missing-import message only when `Lookup(prefix)` is null, as `CheckMemberTarget` already does. Otherwise say e.g. `'x' is a variable; only functions can be called`.

## Findings

### 1. Must fix: a missing import gives three different errors, none of which mentions `import`

Forgetting `import` is the most likely mistake with modules. What happens depends on where the name is used:

| Source (no `import`) | Error |
|---|---|
| `text.put(1, 2, 3)` | `Expected end of statement, found '('` |
| `x = c64.SCREEN` | `'c64' is not declared` |
| `asm { jsr c64.chrout }` | `Unknown member '.chrout'; assembly only has .lo and .hi` |

The first message is misleading, and none of them say how to fix it (CLAUDE.md: "Error messages say what is wrong and how to fix it").

`Parser.cs:591` only joins `name.member` when `name` is imported. For any other name it returns a `NameExpr`, and the `.put(` that follows does not parse. A fix: when an undeclared name is followed by `.member`, report `'text' is not declared. To use the module text, add 'import text' at the top of the file`. One way is to let the parser join `name.member` whenever `name` is not a declared name, and let `NotDeclared` (`Checker.cs:101`) give the hint for a dotted name whose first part is not imported. The asm operand path (`Checker.Asm.cs`) needs the same hint. Add one test per row of the table to `ModuleTests.Reports_errors`.

### 2. Must fix: on Windows, a module can be loaded twice under names that differ only in case

`ModuleLoader.Find` (`Module.cs:85`) uses `File.Exists`, which ignores case on Windows. `loaded` (`Module.cs:47`) is keyed by the name as written, with case. So `import Util` in one file and `import util` in another load the same file twice, as two modules with separate variables:

```
// util.tern
var hits: u8
fn hit() { hits += 1 }

// other.tern
import util
fn go() { util.hit() }

// k.tern
import Util
import other
fn main() { Util.hit(); other.go() }
```

This compiles without an error, and the program has `Util.hits` at `$02` and `util.hits` at `$03`, plus two copies of `hit`. Each call counts in a different variable. This breaks spec 2.2 ("A module is loaded once"), and the same source fails on Linux (`Cannot find module 'Util'`).

Fix: after finding the file, compare the name as written with the file's actual name (for example from `Directory.GetFiles(dir, file)`), using an ordinal comparison. If they differ, report `The module file is named util.tern; write 'import util'`. Add a test (it runs on Windows; on other systems the file is not found, which is also an error).

### 3. Suggestion: import cycles give a misleading error for constants

The status file lists this as a known limitation, but the message is wrong, not just unhelpful. Spec 2.2 says "Modules may import each other", and this valid program fails:

```
// a.tern                    // b.tern
import b                     import a
const N = 4                  var buf: [u8; a.N]
fn fa() { b.fb() }           fn fb() { buf[0] = 1 }
```

`b.tern:2:15: error: 'a.N' is not declared`. `a.N` is declared; it is processed after `b`. At least, the message should say so: when `m.name` is not found and module `m` has not been declared yet (part of a cycle), report `'a.N' cannot be used in a declaration of b: a and b import each other, and a is declared after b. Move N to b, or to a module both import`. Whether such programs must work is a question for the spec session.

### 4. Suggestion: VICE labels can clash

`TernCompiler.cs:105` writes `.` as `_` in VICE labels. A main-file function `util_bump` and the module function `util.bump` both become `.util_bump`, at different addresses (seen in a probe's `.vs` file). Frame variables had the same issue before (`f.x` and a global `f_x`), but modules make it more likely. VICE accepts only one address per label name, so one of them is lost in the monitor. Low priority; a separator that cannot appear in a Tern identifier would avoid it, if VICE accepts one.

### 5. Suggestion (for the spec session): the `math.mul8` shape in spec 11

Spec 11 lists `math.mul8(a, b)` as `lda a` / `ldx b` / `jsr math.mul8`. The compiler generates `ldx b` / `lda a` / `jsr math.mul8`, because it always loads A last. Same size and cycles. The spec table could show the compiler's order, so the two do not look different.

## Probes

All compiled to correct code (listings read by hand):

- Module variables: `util.counter = 5`, `util.counter += 1` (`inc util.counter`), `util.w += 1` (u16, `inc` / `bne` / `inc`), `math.remainder16.lo`.

- Fixed inputs: `fn r(3 using X, v: u8 using A, true using carry) @ $C000` called with `r(t[i] + 1)` gives `ldx i` / `lda t,x` / `clc` / `adc #1` / `ldx #3` / `sec` / `jsr $C000`. X is loaded after A's expression has used it, and the carry is set last.
- Spec 11 shapes: `c64.chrout(a)` is `lda a` / `jsr $FFD2`; `c64.get_cursor()` is `sec` / `jsr $FFF0`; `c64.cursor(5, 10)` is `ldx #5` / `ldy #10` / `clc` / `jsr $FFF0` (the 6.6 example).
- Errors: a parameter or local named like an imported module, `import` twice, a missing module, an unclosed `(` across lines (`Expected ')', found 'var'`, on the next line, which is reasonable).
