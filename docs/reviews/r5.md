## Findings

### 1. `Assembler.Assemble` and `Allocator.Allocate` are not split or listed (must fix)

`src/Tern.Compiler/Backend/Assembler.cs:108-478` (371 lines) and `src/Tern.Compiler/Backend/Allocator.cs:65-306` (242 lines) are unchanged from `main`.

Finding backend 12 (`code-quality-backend.md:165-169`) names them first. Its fix splits `Assemble` into layout, variable placement, and encode-and-list, and `Allocate` into zero page, regions and the RAM block. The status table's row for backend 12 says "fixed" and "`Assembler.Assemble` and `Allocator.Allocate` were split earlier (both under 100 now)", which is not so. Neither is in the Known limitations list of methods over 100 lines.

R5's "done when" asks for the method-length convention, with each method over 100 lines listed. `Assemble` is over 300 and is not a single `switch` or lookup: it lays out sections, places variables, grows branches, checks overlaps, encodes and lists. By `CLAUDE.md` it must be split.

Fix: split `Assemble` as the finding says (its local functions `Lay`, `Flush` and `Merge` are natural seams). Split `Allocate`, or list it with its reason. Correct the backend 12 row. The listings must stay byte for byte the same, which `BenchmarkTests` and the examples above check.

### 2. `Check` misses allocation and layout errors, but its documentation says it reports the same errors (suggestion)

`TernCompiler.Check` (`TernCompiler.cs`, the summary of `Check`) says "The checks are those of `Compile`, which reports the same errors". `CheckResult.Ok` says "No errors: the program can be built". Errors found after the checks are not reported.

Failing case:

```
var a: [u8; 200] @ zp
fn main() { a[1] = a[0] }
```

`Check` returns `Ok = true` with no errors. `Compile` fails with "Zero page is full: '@ zp' variables need 200 bytes, 146 are free...". A language server would show such a program as clean.

Fix: say in both summaries that allocation, code generation and layout errors (zero page, areas, fixed addresses) come only from `Compile`. Running the allocator in `Check` is M28's decision, not R5's.

### 3. Recovery fixes without a test (suggestion)

Status lists two changes to error recovery with no test that shows them:

- Syntax 20: the statement column is now restored after an error in a block.
- Semantics 18: a top-level declaration checked on demand starts with a fresh body state.

I tried five recovery programs on `main` and on the branch, and all gave the same errors. If a program exists whose errors differ, add it as a test. If none can, say in the status rows that the change is not observable.

### 4. Small things (suggestion)

- `Module.cs:177-179`: the summary "Whether a folder is the library or one of its platform folders." now sits above the new `SourceFiles` class, which has two summaries. `InLibrary` has none.
- `Checker.cs`, `Entry`: the doc says `Main` is "null after an error", but the type is `FunctionSymbol`, not nullable.
- `Checker.DeclareFile` ends with a blank line before its closing brace.
- `Lexer.cs`: an `Error` token's `Start`/`End` is the end of the line it skipped, not where the error is. Nothing reads it yet, but M28's error ranges will need the error's own place.
- A `///` comment carries over blank lines and plain `//` comments to the next token. That is the usual rule (Rust does the same), but the M28 spec session should confirm it, since the spec says nothing yet.
