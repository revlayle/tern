## Findings

### 1. `-o` can still overwrite a module the program imports (must fix)

- Where: `Cli.cs`, `Clash` (compares the outputs with `input` only), called from `CompileCommand`.
- What: tools 3 is "`-o` can overwrite the source file". The fix compares each output path with the main file and with the other outputs. An imported module is source too, and nothing compares the outputs with it.
- Failing case: `util.tern` holds `var n: u8` and `fn bump() { n += 1 }`. `main.tern` holds `import util`, `var out: u8` and `fn main() { util.bump() ; out = 1 }`, on separate lines.

```
tern --target c64 main.tern -o util.tern
Wrote util.tern          exit 0; util.tern now holds the 36 program bytes
```

  The listing, label and `.lines` paths work the same way: `-o util.prg` is safe, but an output named after any imported module's `.tern` file replaces it. The interface module `<name>.tern` that a binary writes can collide with an imported module of that name too.
- Fix: pass `Clash` the paths of every module the compile loaded (the main file and its imports from the source folder, library modules aside), not just `input`. For example, take them from `CompileResult`, or from the loader's module list. Add a `CliTests` case with an imported module as `-o`.

### 2. The non-ASCII name error prints the character in the console's code page (suggestion)

- Where: `Lexer.cs`, `NotAscii` (`'{source[at]}' cannot be in a name`); `Tern.Cli` sets no output encoding.
- What: on Windows, the output (and the `--json` output) is written in the console's OEM code page. `é` comes out as byte `$82` (code page 437), and `α` or `٣` come out as `?`. So the message becomes "'?' cannot be in a name". This affected every message that quotes source text before R3, but this is the first message whose whole content is the character. `--json` output that is not UTF-8 is also a problem for agents.
- Fix: name the code point too, as the raw-byte message already does: "'é' (U+00E9) cannot be in a name". Separately (tools area, R5 or R6): write UTF-8 (`Console.OutputEncoding`) at least under `--json`.

### 3. The internal-error catch has no test (suggestion)

- Where: `Cli.cs`, `Run`'s `catch (Exception e)` (exit code `InternalError` = 4, JSON under `--json`).
- What: no test reaches it, so its JSON shape and exit code, which the help documents, are not guarded. No input reaches it on purpose, which is the point of the catch.
- Fix: a test that makes `Cli.Run` throw from inside. For example, an `output` `TextWriter` that throws on its first write after the command starts, or an internal hook for tests. Check exit code 4 and the JSON with `"ok": false`.

### 4. The depth limit counts the enclosing block and expression (suggestion)

- Where: `Parser.cs`, `Enter` and `MaxDepth`; `Parser.Statements.cs`, `ParseBlock`.
- What: `out = ((…1…))` with 255 pairs of parentheses in `main` is already an error ("nested more than 256 deep"), because the function body and the outer expression take two levels. The message says "more than 256" about a program whose deepest visible nesting is 255. This is harmless, but the number a user reads is not the number they wrote.
- Fix: add this to question 173 for the spec session, which already asks whether 256 is right and whether the spec names it. Either say "about 256", or leave function bodies uncounted.

### 5. `docs/status.md`: `Lexer.Tokenize` is not listed, and one NES line is out of date (suggestion)

- `Lexer.Tokenize` (`Lexer.cs:129-352`) is about 223 lines, and R3 added about 25 of them (the comment newline, the ASCII checks, `0x`, `NotAscii`). The method-length convention asks for each method over about 100 lines to be listed with its reason, and "Long methods R3 touched" names only `Cli.Run` and `Runner.Run`. Most of its length is the local `Next`, a single dispatch on the character, which may read best whole. Say so in the list.
- Known limitations, the NES line: "models no timing within a frame (sprite 0 hits, the length of vblank)". The length of vblank is now modelled (tools 9). Drop it from the list.

### 6. Finding 19's general `name {` case (suggestion)

- Where: `Parser.Statements.cs` (the new `emit {` case).
- What: the finding's fix also suggested "A struct literal is only an initial value" for any `name {` at the start of a statement. `foo { lda #1 }` still gives "Expected '=' and the value of 'lda', found '#'". The three messages the finding lists are fixed, so this is the remainder. `P { x: 1 }` already gets a good message for another reason.
- Fix: optional, in R6 (messages as data) or here. Note it in the syntax 19 row either way.
