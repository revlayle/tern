## Findings

### 1. `Dispatches` turns off a return's dead-load check in the whole function (suggestion)

- Where: `Optimizer.DeadStores.cs:575, 591` (`RemoveDeadLoads`), `Optimizer.Registers.cs:276` (`NzLiveAfter`), `Optimizer.DeadStores.cs:755` (`Dispatches`).
- What: when a function has any `LabelTable`, every compiler `rts` in it is treated as a possible dispatch, so no load before any of its returns is removed. The fix is correct and nothing in the benchmarks moved. Even so, it is coarser than what `RegistersLive` does at `:344`: a dispatch `rts` there joins what the table's labels read.
- Fix: none needed now. Backend 9 (R4, one table of instruction effects with control flow) should replace both checks with the jump-table liveness. Give the R4 row for backend 9 a note that `Dispatches` is the interim form.

### 2. Backend 6 has no test (suggestion)

- Where: `Assembler.cs:401`. The table row says "none: not reachable".
- What: R2's "done when" asks for a test that fails before each fix. No source program reaches a long branch with a label offset. But `Assembler.Assemble` is public, and it takes a list of `AsmItem`. A test can build `bne label+3` with the label more than 127 bytes away, and check the `jmp` operand.
- Fix: add that unit test (about 10 lines), or keep the row's reason. Either is acceptable. The row already says why there is no test.

### 3. Spec 5.1 on a variable bound with a literal end past 255 (suggestion, for the spec session)

- What: spec 5.1 (line 483) says "With a variable bound, the type comes from the bound's type". Read that way, `for i in start..256` with `start: u8` should count with a `u8` (`start` to 255, ending on `inx` / `bne`). The compiler rejects it instead: "256 does not fit in u8 (0 to 255), the type of 'start' ... Convert 'start' with 'as u16'". `main` does the same, so this is not new. The error is safe, and its fix compiles.
- Fix: no code change in R2. Ask the spec session whether `u8_var..256` should be allowed, the natural way to walk from an offset to the end of a page. If it is, the branch's `f.To.Type = type` path (`Checker.Bodies.cs:273`) already handles the end, and the generator's `to != 256` test (`CodeGen.Loops.cs:538`) already gives the right loop. The `Unify` error would have to allow exactly an end of 256.

### 4. The last fallback message is generic (suggestion)

- Where: `Checker.TypeRules.cs:113`, "Expected {target}, found {source}. Use a {target} here".
- What: it now follows the fix-verb convention. But for types with no conversion, such as one array type for another, "Use a [u8; 4] here" adds little. It is reached rarely, since structs, reals and bools have their own messages.
- Fix: none needed for R2. R6 (messages as data) can revisit it.
