### Findings

**1. Must fix: every fixed-address variable of the interface module must be `data` in the binary, not only the `volatile` ones.** `Checker.cs` (`MatchInterface`, the loop over `VariableSymbol { FixedAddress: not null, IsData: false }`) requires `data` for any fixed variable. Decision 2026-11-03 says "each of its `volatile` fixed variables (data every level provides)", and the skill (`language.md` section 12) says "`volatile var`s the binary defines as `data`". An interface that also names a host variable the levels may read stops every level from building, with a fix that would overwrite the host's memory when the level loads:

```tern
// level_api.tern
const SLOT_FIRST = $6000
const SLOT_LAST = $6FFF
fn setup() @ $6000
fn enter() @ $6003
var lives: u8 @ $0340        // the game's, read by levels
```

```tern
// level.tern
import level_api
memory {
    level_api.SLOT_FIRST..=level_api.SLOT_LAST  program
    $FB..=$FE zeropage
}
export level_api
var n: u8
fn enter() { n = 1 }
```

gives "'level_api.lives' is data every binary of level_api provides. Declare 'data lives: u8 @ $0340 = ...' in the main file". The same happens with `var border: u8 @ $D020`. Check only variables declared with the `volatile` keyword, as the decision says, and add a test that a plain fixed variable of the interface is not checked (and can be used by the level). The spec's error bullet ("a variable of the module with no `data`") reads wider than the decision; if the coding session thinks the wider rule is right, ask the spec session instead (another possible rule: the variables whose address is in the binary's program areas), and make the skill match either way.

**2. Suggestion: a routine outside the first program area gives a message that names the table, not the routine.** With `fn far() @ $7000` in an interface whose slot is `$6000-$6FFF`: "The jump table (4099 bytes) must be at the start of the first program area, but it does not fit in $6000-$6FFF. Make the first area larger". The fix is usually to move the routine in the interface. Name the routine and its address when the table is laid out by `export level_api` (`'level_api.far' at $7000 is outside the first program area $6000-$6FFF. Move it ...`).

**3. Suggestion: an export table over the startup code says "Move the data".** `export add @ $0820` in a small program: "'export table' at $0820-$0822 overlaps the BASIC line and startup code at $0801-$0821 ... Move the data, or start the program area lower". The table is not data; "Move the export table" (or "Give the table a higher address") fits.

**4. Suggestion: misplaced doc comment.** `TernCompiler.cs:382-386`: `CheckExportTable`'s `<summary>` was inserted under `CheckFixedData`'s, so `CheckExportTable` has two summaries (the first describes fixed data) and `CheckFixedData` has none. Move the fixed-data comment back down to `CheckFixedData`.

**5. Suggestion: missing tests for paths that work.**
- Several `export` lines in a program with `main`, one with the `@` (question 91b): only the error with two `@` is tested, not that `export add_score` plus `export beep @ $0900` gives a two-entry table in that order.
- An export table in a `reserved` area (question 91a): only "not in a program or reserved area" is tested. Note that a table in a reserved area far from the code makes the program file cover the gap: `export add @ $C000` with `$C000..=$C0FF reserved` writes a 47 KB `.prg` (`$0801-$C002`). This is how fixed `data` in a reserved area already behaves, but it may surprise; the guide could say so.
- `export level_api, level_api` ("Remove the second 'level_api'") has no test.

**6. Suggestion: the CLI help does not mention the program's export table.** `Tools/Cli.cs:24` says "A program with 'export' lines and no main is a binary ... it also writes <name>_api.tern". A program with `main` and `export f, g @ addr` writes `<name>_api.tern` too.
