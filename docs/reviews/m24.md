## Correctness: what I checked

I read every routine against the format: value = ±M × 2^(E − 152), with M the 24-bit mantissa including its leading 1.

- **add/sub.** The swap puts the larger magnitude in A, so `we − eb` is never negative. The byte loop folds each byte shifted out into `wt`, and the bit loop sets `wt` from the carry. The sticky bit is ORed into bit 0 of the guard byte. A shift of 32 or more leaves only the sticky bit. After a subtraction, `normalize` shifts left at most one bit unless the exponents differ by 0 or 1. In that case no bits were lost, so the guard bit that decides rounding is always exact. The carry out of an addition goes back in through `ror` and `inc we`.
- **mul.** The exponent is `ea + eb − $80`, done in 16 bits, so underflow is negative and overflow goes above 255. The 48-bit product is kept whole. Only the guard byte and the bit below it are used, and that is enough for halves away from zero: rounding up depends only on the first bit below the result, so no sticky bit is needed.
- **div.** 32 quotient bits with exponent `ea − eb + $81`. The remainder stays below 2·Mb, so it fits in `wc`'s 4 bytes. The carry left by the compare is the quotient bit on both paths.
- **finish.** Rounds first, then checks the range: a result that rounds up to 2^-128 is kept, and a 16-bit exponent of 0 or less becomes 0.
- **int_part, to_/round_.** The shift is `152 − we − round`. Exponent 128 with rounding gives 1, and exponent 127 gives 0. A rounding carry into 2^24 is treated as too large. -32768 is accepted by `to_signed` and -32768.5 is not.
- **trunc/floor.** `chop` never clears the leading bit (we ≥ 129). In `floor`, the carry chain relies on `cpy #4` leaving the carry clear, and a carry out of the top byte becomes `$80` with `we + 1`.
- **dec/to_digits.** M × 10^9 < 2^54 fits in 8 bytes. The largest whole value is 127 bits, which fits in 16. The last single-bit shift leaves the rounding bit in the carry. The BCD size n + (n+3)/4 is enough for 8n bits. Decimal mode is cleared on every path that sets it.
- **of.** Multiplying by a power of 2 is exact for a double, so `round(a * pow(2, 24 − e))` rounds the double's exact value once. A mantissa that rounds up to 2^24 is renormalized before the range check.

## Findings

1. **Suggestion: the error for `float.of` of a value too large tells the user to do the wrong thing.** `float.of(2e38)` gives

   ```
   ...\lib\float.tern:75:32: error: Index 1 is outside the array (length 1) (called from big.tern:2). Use an index from 0 to 0
   ```

   and `--json` reports `"suggestion": "Use an index from 0 to 0"`. The spec only asks for an error, so this meets 10.1. But it points at library code, and its fix sentence is about an index the user never wrote. The comment at `float.tern:72` explains the trick only to someone who opens the file. This is question 128 (an `assert` in a `const fn`). Until that is settled, the skill's error section or the `of` row in `language.md` could say what this error means.

2. **Suggestion: `div` and `mul` loops use work bytes in absolute memory.** `wc`, `wd`, `wa` and `wb` are outside zero page. Each `lda`/`sta`/`rol` in the 24- and 32-step loops costs a cycle more than it would in zero page. The status file already estimates about 1,000 cycles saved for `div`. That would cost more zero page: the module already takes 19 bytes there once any routine is used. This is a trade-off for later, not a defect. The 19 bytes would be worth listing in the spec's `float` section when the sizes are copied in.

3. **Note: an `add`/`sub` with a 0 operand returns without storing** (`float.tern:261-263`). If `p` holds a non-canonical zero (exponent 0, mantissa bytes not 0), `add(p, zero)` leaves those bytes as they are. Question 129 says "every routine stores 0 as four zero bytes", which is not true for this one case. Such a value can only come from bytes the program wrote itself, and every routine treats it as 0, so nothing goes wrong. Either reword 129 ("every routine that stores 0 writes four zero bytes"), or leave it.

4. **Note: a leftover `Replace` in `InlineAsmTests.cs:150`** (on `main`, not this branch). `.Replace("lda " + a + "\n", "lda #" + a + "\n")` matches nothing on any checkout, since the text already says `lda #{{a}}`. Unlike the two `ImplementsTests` fixed in `b21169a`, the test does not depend on it. It could be removed sometime. The other `"\n"` patterns in `Replace` calls are safe: `PluginTests` normalizes its strings with `ReplaceLineEndings("\n")`.

## Tests

- `FloatTests` covers what the roadmap asks for. Add, sub, mul and div are tested over all pairs of 71 values (edges, near 1, random) plus 1500 random pairs with close exponents each. The overflow flag is checked too, and q is checked to be unchanged. There are tie cases, including one where only the sticky bit keeps the result below the half. Also covered: overflow, division by zero, 0/0, underflow to 0, the flag staying set; neg/abs/copy/is_zero/cmp (also a 0 with its sign bit set); about 2,000 `from_` values; `to_`/`round_` at every limit and halves; `trunc`/`floor` on negatives, below 1, at 2^23 and the carry into a new bit; `dec` at 0-10 decimals over about 100 values; `of` at ties at both ends of the range, and its error.
- The model computes exact fractions and does not copy the 6502 algorithm, as decision 2026-11-13 asks.
- `StructLiteralTests`: a const fn, `repeat`, a list built with `for`, a `data` array of structs, a `[u16; 2]` field; the errors for a wrong length, an element out of range and a real element.
- Not tested: the result pointer equal to the operand pointer (probed above, correct). Adding `add(p, p)` and `mul(p, p)` would protect it if the routines are reordered later.

## Spec conformance

- Format, rounding, overflow and underflow, and the API match 10.1 and the decision. The value range (2^-128 to (1 − 2^-24)·2^127) matches the spec's "about 2.9e-39 to 1.7e38", which fixes how "exponent plus $80" is read (question 126).
- The struct literal rule matches 3.3: the error for a wrong length names the field, the expected and found lengths, and starts its fix with a verb ("Return an array of 4 values").
- Behaviors the spec does not fix are listed as questions 126-130. I agree with the proposals. For 129, see finding 3.
