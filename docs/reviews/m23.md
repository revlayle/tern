### Findings

**1. Suggestion: a declaration that starts with a word from another language still causes follow-on errors.** `Parser.DeclaredName` (`Parser.cs`) finds the name only when the declaration starts with a Tern keyword. A habit from Rust or JavaScript makes the parser skip the whole declaration without breaking its name, so every use is reported again:

```
var g: u8 = 0
pub fn helper() {
    g = 1
}
let count: u8 = 0
fn main() {
    helper()
    count = 2
}
```

gives 3 errors: `Expected 'const', 'var', 'data', 'struct' or 'fn', found 'pub'`, then `'helper' is not a function` (7:5) and `'count' is not declared` (8:5). Spec 13 says a name whose declaration has an error adds no errors at its uses. Two possible fixes: `DeclaredName` could skip one unknown identifier before `fn`/`var`/`const`/`data`/`struct`, or treat `let name` like `var name`. Errors for these habits (spec 13, "Errors for habits from other languages") would be better still, but that is a spec change.

**2. Suggestion: an unclosed `(` hides the rest of its block.** The lexer gives no line breaks inside `( )`, so after `g = (1 +` the skip runs to the `}` that closes the block. Errors on the following lines of that block are lost:

```
fn main() {
    g = (1 +
    g = 2
    g = 500      // not reported
}
```

gives `Expected ')', found '='` only. The roadmap lets the coding session decide how lines inside brackets are skipped, so this is within scope. `ExpectEnd` already ends a statement at a declaration on a new line after an error. Doing the same for a line that starts at the failed statement's column would keep the later errors. Low priority.

**3. Suggestion: a local whose initializer uses a broken name is broken too, which hides later errors.** With `var e: Enmy` (a misspelled type), `var k: u8 = e.x` stops at `e` with `FollowOnError`. `CheckBlock` then makes `k` an `ErrorSymbol`, so `k = 999` on a later line is not reported, although `k`'s type is written and nothing is wrong with that line. This matches the roadmap's "bad initializer gets an error type" and loses no error that matters on the first pass. A local with a written type could keep that type, and only the initializer would be skipped. This is not needed for M23.

**4. Suggestion: a doc comment was separated from its member.** In `Checker.cs`, around line 248, the new "Going on after an error" section was inserted between `/// <summary>The name of the root that stands for a binary's entries ...` and `private const string EntriesRoot`. The summary now sits above the section marker, `EntriesRoot` has no doc comment, and the section ends in the middle of the export code. Move the section above the summary (or to the end of the file).

## Second review (`2f8078f`), 2026-11-12

**Ready to merge.** All four suggestions are done, each in its own commit with a test. 2892 compiler tests and 36 CPU tests pass. `BenchmarkTests` and `SkillTests` pass with no baseline change. I compiled the first review's programs again with a freshly built `tern`.

- **Suggestion 1** (`4a9d900`): `pub fn helper()` and `let count: u8 = 0` now each give one error. The calls to `helper` and the uses of `count` add none. `StartsCurrentDeclaration` and `DeclaredName` accept an identifier before `fn`/`var`/`const`/`data`/`struct`, and `let name`.
- **Suggestion 2** (`b0b85cf`): after `g = (1 +`, the next line that starts no further right than the failed statement starts a new statement. `g = 500` on the following line is now reported. If the continuation line is indented further (`(1 +` / `    2`), it is still skipped as part of the statement, and the next statement is checked. The rule only applies in `SkipStatement` after an error, and in `ExpectEnd` once an error has been found. In both places the lexer has given no line break, so valid code is not affected.
- **Suggestion 3** (`a5bbe5a`): a local with a written type keeps that type when its initial value fails. `var k: u8 = e.x` / `k = 999` reports the 999, as do `var x: u8 = 300` / `x = 301` and `var y: u8` (no value) / `y = 301`. A local without a written type (`var j = e.hp`) stays broken, which is right, since its type is unknown.
- **Suggestion 4** (`f884a38`): the summary is back on `EntriesRoot`, and the recovery section is a block of its own.

### Findings

**5. Suggestion (from the first round, not a regression): an `else` on its own line after an `if` whose condition has a syntax error is reported too.**

```
fn main() {
    if g == ) {
        g = 1
    }
    else {
        g = 2
    }
}
```

gives `Expected an expression, found ')'`, then also `Expected an expression, found 'else'` (6:5). An `else` on the line after `}` is valid when the condition is correct. `SkipStatement` stops at the line break (or, since `b0b85cf`, at the column) after the `}`, so the `else` is parsed as a new statement. The commit before `b0b85cf` gives the same result. When the skip has just closed a brace, it could continue past an `else` at the start of the next line. This is a small fix and can be done after the merge.
