# Review: M27, NES

Branch `m27-nes` (`036c376` to `fbb764a`, 11 commits), from `main` at `35de89e`. Roadmap "M27: NES"; spec 2.1, 4, 8.4, 8.5, 12.2, 14.1; decisions 2026-11-14 and question 150.

## Verdict

**Not ready to merge.** Four things must be fixed:

1. An `overlay` area on the NES builds a file that no cartridge can use.
2. A `region` in the RAM mirrors (`$0800-$1FFF`) silently aliases zero page and the variables.
3. `tern run`'s index check reports false errors in bank code, and does so on the done-when example.
4. NROM-256 cannot hold a table or function larger than 16 KB, although spec 12.2 gives NROM one ROM at `$8000-$FFFF`.

Every "done when" item is met. I ran both examples in Mesen 2.1.1 myself.

`dotnet test` (in `../6502-language-dev`, on `fbb764a`): 3704 compiler tests and 36 CPU tests pass. No benchmark changed. `SkillTests` pass.

## What changed

- **Apple II prefix code only with `io`** (question 150). The two new tests in `Apple2IoTests` check the listing and the report line.
- **`cartridge` line, boards and `Platform.Nes`.** The memory map, the volatile area and "no default encoding" match spec 12.2. The `cartridge` line is required on the NES, also with no memory block. Board and option errors list the choices. `program` lines on the NES give "not supported yet".
- **Startup** (`TernCompiler.Nes.cs`). I read it in the scroll example's listing. The order is `sei`, `cld`, `$4017`=`$40`, `txs`, `$2000`/`$2001`/`$4010` = 0, `stx bank_zero` on UxROM (a 0 in the fixed bank, so the bus conflict is safe), `bit $2002`, two vblank waits with `$0000-$07FF` cleared between them, zero-page initial values (zeros skipped), the copy, `jsr main`, `jmp halt`. This matches the spec. The copy's remainder loop (`lda initial-1,x` / `sta bss+N-1,x`, X from `rest` down to 1) is right. I checked it with more than 256 bytes of initial values (200 + 200 + 2): all values are right after the copy.
- **Vectors.** Reset is always the compiler's. Unset NMI and IRQ point to an `rti`. `data` over `$FFFC`, a plain `fn`, a part, `addr(h) + 1` and data outside ROM are all errors. Code is kept out of `$FFFA-$FFFF`, also when fixed data sits just below the vectors.
- **iNES output.** The header (mapper nibbles, mirroring bit 0 = vertical, PRG and CHR counts) is right. A two-table NROM-256 program (2 × 9000 bytes) runs correctly in `tern run`. UxROM's bank count is the highest bank + 2, rounded up to a power of two. Bank 15 is rejected as the fixed bank.
- **`chr` areas and `@ area + offset`.** Indexing tile data is an error. `addr()` of tile data is a `u16`. Overlaps, offsets past the end, a second `chr` line and `chr` on UxROM are errors. The region-offset overlap rule works on the C64 too.
- **Banks.** `@ area[n]`, filling a bank in import order, the bank-to-bank call error, bank-number errors and `implements` all behave as spec 8.5 says.
- **`tern run`** (`NesBus`). I checked PPU address/data, the buffered read and the palette read, the palette mirrors (`$3F10/14/18/1C`), vertical and horizontal nametable mirroring, increment 32, the `$2002` latch reset, OAM DMA cycles, the controller shift with 1s after the eighth bit, and the UxROM latch with its bus conflict.
- **`lib/nes`.** `pad` reads `$4015+n` (n = 1 or 2). `vblank` sets OAMADDR to 0 before DMA. `frames` is shared between main and the NMI, so it is volatile through the call graph, and `wait_frame` re-reads it in its loop.
- **Mesen labels.** Bank code is written at its bank's PRG offset (`art_load` at `0000`, `motion_update` at `4000`), and the fixed bank at its own.

## Findings

### 1. Must fix: an `overlay` area on the NES builds an unusable file

`src/Tern.Compiler/Semantics/MemoryLayout.cs:166`. `overlay` is accepted on a cartridge, and the build writes an overlay file named `.nes` that holds an `$FFFF`-headed segment (Atari-style), not an iNES image:

```
import lv1 @ lv                // lv1.tern: fn f() { }
memory {
 cartridge nrom vertical
 $6000..=$7FFF overlay lv
}
fn main() { lv1.f() }
```

This writes `lv1.nes` (`FF FF 00 60 00 60 60`) and reports "Overlay area lv $6000-$7FFF: lv1.nes". A cartridge has no loader, and NROM and UxROM have no RAM at `$6000`. Spec 8.4 says the board lists which kinds it accepts, and "another target's kind is an error". Make `overlay` an error when the build is a cartridge, with a fix that points to `bank` areas. Add a test.

### 2. Must fix: a region in the RAM mirrors aliases zero page and the variables

`src/Tern.Compiler/Semantics/MemoryLayout.cs:161` (`region`), together with `NesBus.Read`/`Write`, which mirror RAM as the hardware does. On the NES, `$0800-$1FFF` is `$0000-$07FF` again, but a region there is accepted and placed as separate memory:

```
memory {
 cartridge nrom vertical
 $0800..=$08FF region mirror
}
var m: [u8; 4] @ mirror
var score: u8 @ zp
fn main() {
  score = 7
  m[0] = 99
}
```

`tern run --target nes ... --dump score` gives `score $0000 u8 = 99`. The same happens on hardware. A region at `$6000-$7FFF`, or anywhere outside RAM, compiles too, and its writes go nowhere. The `program` line already gives "not supported yet" on the NES. A `region` (and a `reserved` range, which only matters for fixed data) should likewise be limited to memory the board has: `$0200-$07FF` for regions, plus zero page. Give an error that names the RAM range. Add a test for a mirror and for `$6000`.

### 3. Must fix: `tern run`'s index check ignores the selected bank

`src/Tern.Compiler/Tools/IndexChecker.cs:26`. The checks are keyed by address alone (`GroupBy(i => i.Address).First()`). Two banks share `$8000-$BFFF`, so an instruction in one bank is checked as if it were the instruction at the same address in the other. On the done-when example:

```
tern run --target nes examples/nes/scroll.tern --cycles 3000000
Index check (the program has no check; the emulator found these):
  motion.tern:29: Index 4 is outside 'motion.x', which has 4 elements (448 times)
```

`$8058` is `lda motion.x,x` in bank 1, but `sta art.fill.tile` in bank 0, which runs with X = 4..31 while `art.load` draws the ground: 8 rows × 28 columns × 2 nametables = 448. The run's profile and the function entries (`Entered`) are also keyed by address, so `tern bench` and the profile attribute bank code the same way.

`The_scroll_example_scrolls_and_moves_its_sprites_with_code_in_two_banks` calls `Runner.Run` directly and never looks at `IndexErrors`, so the test passes. Fix: key the checks (and the profile's function names) by bank as well as address, using `NesBus.SelectedBank` for addresses in the bank window. Then assert in the scroll test that `IndexErrors` is empty.

### 4. Must fix: NROM-256 cannot hold anything larger than 16 KB

`src/Tern.Compiler/Cartridge.cs:255`. NROM's code areas are two separate 16 KB areas (`$C000-$FFFF`, then `$8000-$BFFF`), so that small programs come out as NROM-128. Since functions and `data` are placed whole (8.4), a table over 16 KB has nowhere to go:

```
memory { cartridge nrom horizontal }
data big: [u8; 17000] = [i % 251 for i in 0..17000]
fn main() { ... reads big through a pointer ... }
```

The error is "'big' needs 17000 bytes, and no program area has room for them in one piece ... Make an area larger, or split the code into smaller functions". Neither fix is possible: `program` lines are "not supported yet" on the NES. Spec 12.2 gives NROM one ROM area, `$8000-$FFFF`, and decision 2026-11-14 says the size follows from the program. A level map or a large table over 16 KB is a normal NROM-256 program. Fix: when the program does not fit in `$C000-$FFF9`, lay it out again with one area `$8000-$FFF9`. Add a test with a 17000-byte table. If the split is intended, raise it as a question for the spec session, and change the error's advice.

### 5. Suggestion: running out of RAM gives advice that does not apply

`src/Tern.Compiler/Backend/Assembler.cs` (the "no program area has room" error, used for the variables' block). With 7 × 256 bytes of globals on the NES:

`i1.tern:1:1: error: The variables need 1792 bytes, and no program area has room for them in one piece (code is never split across areas). Areas: $C000-$FFF9: ...; $8000-$BFFF: ...; $0200-$07FF: 0 of 1536 bytes used. Make an area larger, or split the code into smaller functions`

On the NES this will be common (2 KB of RAM). The message should name the RAM (`$0200-$07FF`, 1536 bytes), leave out the ROM areas, and suggest `data` for tables that never change, `@ zp`, or smaller arrays. It also points at line 1, column 1.

### 6. Suggestion: three NES error messages are misleading

- `TernCompiler.Nes.cs:83`: `data v @ $0300` (with a `reserved` line) says "Make it a 'var' with an initial value". Written with its `@ $0300`, that gives "A variable at a fixed address cannot have an initial value". Say "a 'var' without the fixed address".
- `MemoryLayout.cs:186`: `$8000..=$FFFF reserved` on NROM gives "the reserved and region ranges cover all of $8000-$07FF". The range comes from `LoadAddress`/`RamEnd`. On a cartridge, name the board's code areas.
- A call between banks (`Checker`, `NeverTogether`) says the modules "are never loaded together" and suggests "put one of them in another area". Banks are switched, not loaded, and the usual fix is to put both modules in the same bank.

### 7. Suggestion: the report lists RAM under "Program areas"

Every NES report lists `$0200-$07FF: N of 1536 bytes used` under "Program areas". That happens because `Assembler.Assemble` appends the variable areas to the free list. The report already has "Variables in RAM: ..."; list the RAM line separately, or leave it out.

### 8. Suggestion: a vector may point into a bank

A program with `data v: u16 @ $FFFE = addr(k2.irq)`, where `k2` is in `w[0]`, compiles. The interrupt then jumps into whichever bank is selected. That is legal under 8.5 (resident code may take addresses in any bank), but the vectors fire in every bank, so it is almost always a mistake. Consider an error, or a question for the spec session.

### 9. Suggestion: follow-on error after a rejected `bank` line

With `cartridge nrom` and `$8000..=$BFFF bank w`, `import k0 @ w[0]` reports first "The memory block has no overlay area 'w'. Add a line 'first..=last overlay w'", and only then the useful "The board 'nrom' has no banks". The first message should not appear.

### 10. Suggestion: `tern run` gives the NES RAM at `$4020-$7FFF`

`NesBus.Write` (`:161`) stores writes to `$4020-$7FFF` and `Read` returns them. NROM and UxROM have no PRG RAM there, so a program that uses it works in `tern run` and not on the hardware. Ignore those writes and return 0 (or open bus), as for the registers.
