# Review: M6 (match, interrupts, function modifiers) and the M5 follow-up

Branch `m6-match` at `4a280e9`, against `main` at `1eb2998`. Reviewed 2026-11-02.

## Verdict

**Not ready to merge.** Three must-fix items, all small. One makes a program that uses only the public library API compile to wrong code once an interrupt handler is involved; the other two are a valid `match` that fails to compile and a volatile read that is dropped.

`dotnet test`: 810 pass (36 CPU, 774 compiler).

The rest is in good shape: the jump table and compare chain are correct for every byte value (bounds check after `sbc #low` catches values below `low`, signed values via `eor #$80`), handler register saving is minimal and correct, frame placement puts handler frames after every main frame, inline copies get unique asm labels, and the tests are thorough.

## Findings

### 1. Must fix: library work bytes are shared between main and an interrupt handler without an error

`src/lib/math.tern:9-11`, `src/Tern.Compiler/Semantics/Checker.cs:1380` (`OrderRoots`).

`math.mul8`, `mul8_fast`, `mul16`, `div8`, `shl16` and `shr16` all use the private globals `w0`-`w2`. Spec 8.1 forbids a *function* shared between main and a handler, and `OrderRoots` enforces that, but two *different* library functions that share a private global pass the check. The user cannot see or avoid the shared bytes, since they are `private`.

Failing case (run with `irqEvery: 600`): 104 of the 256 products are wrong, with no compile error.

```
import math
var lo: [u8; 256]
var q: u8
interrupt fn handler() { q = math.div8(200, 7) }
fn main() {
    // install handler at $FFFE, cli
    for a in 0..=255 { lo[a] = math.mul8(a, 13).lo }
}
```

Fix: the minimal fix is to report an error when a module's `private` global is used by compiled functions from two roots (main and a handler, or two handlers), naming both functions, with the same reasoning as the existing error. Public globals stay allowed, since they are how main and handlers communicate. A later improvement could move the work bytes into the functions' frames. Either way, the spec session should add a sentence to 8.1.

### 2. Must fix: a dense `match` inside both a `using X` and a `using Y` loop does not compile

`src/Tern.Compiler/Backend/CodeGen.cs:371-376`.

The jump table needs a free index register. If X and Y both hold loop variables, `FreeIndexRegister` throws "No free index register: X and Y are both used by loop variables". That message points at loops, not at the `match`, and the program is valid: a compare chain needs no index register.

```
var out: [u8; 16]
fn main() {
    for i in 0..4 using X {
        for j in 0..4 using Y {
            match j { 0 => out[0] = 1  1 => out[1] = 1  ...  7 => out[7] = 1 }   // 8 arms, one per line
        }
    }
}
```
gives `5:13: No free index register: X and Y are both used by loop variables`.

Fix: use the compare chain when neither X nor Y is free (`_reserved` contains both). Add a test.

### 3. Must fix: a `match` with only `_` drops a read of a fixed-address value

`src/Tern.Compiler/Backend/CodeGen.cs:356`.

With no value arms, the subject is evaluated only if `Simple1` returns null (it might call a function). A fixed-address variable is simple, so its read disappears. Spec 4: "Fixed-address variables are volatile. Every read and write in the source happens exactly once and in order." Some I/O reads have side effects, such as `$DC0D` (it clears CIA interrupt flags).

```
var reg: u8 @ $C000
var r: u8
fn main() { match reg { _ => r = 1 } }
```
compiles to `lda #1 / sta r / rts`, with no `lda $C000`.

Fix: also evaluate the subject when it reads volatile memory, or simply always `GenA` it (the case is rare, so a few wasted bytes don't matter). Add a test.

### 4. Suggestion: each inline copy allocates new temporaries in the inline function's frame

`src/Tern.Compiler/Backend/CodeGen.cs:207`, `GenInline`.

`_freeTemps.Clear()` on entry gives every copy a fresh pool, so the function's frame grows with each call site. With `inline fn f(i: u8) -> u8 { return a[i] + g(i) + a[i ^ 1] + g(i + 1) }` called three times, `f` gets `_t0` … `_t8` (9 bytes of zero page) where 3 would do: the copies never run at the same time. Fix: keep a temporary pool per inline function across its copies (save and restore it as the caller's pool is saved), instead of clearing it.

### 5. Suggestion: the raster example's color changes jitter at the right side of the screen

`examples/raster.tern`. The user saw this in VICE.

This is how the example's timing works, not a compiler bug. The change happens about 58-63 cycles after the raster interrupt is raised: IRQ entry (7 cycles plus up to 7 to finish main's current instruction), saving A and X (8), acknowledging (6), the `match` dispatch (about 29 cycles: `lda`/`cmp`/`bcs`/`tax`/2×(`lda`,x/`pha`)/`rts`), then `lda #c` / `sta $D020`. A PAL line is 63 cycles, so the border write lands near the end of the line, on the right side. Its exact position depends on which instruction main was running, which gives up to 7 cycles (56 pixels) of jitter.

The example is meant to show `match` and interrupt handlers, not a stable raster (the user agreed, 2026-11-02). Fix: add a comment to the example saying that the bars are not stabilized and that their right edge jitters by a few cycles, depending on which instruction main was running when the interrupt came. A stable raster needs a double-IRQ or timer trick, which is beyond this example. Leave the code as it is.

The "done when" item (runs in VICE) is met.

### 6. Suggestion: misplaced doc comment

`src/Tern.Compiler/Semantics/Checker.cs:1373`. The old `/// <summary>Functions reachable from main, callers before callees. Reports recursion.</summary>` was left above `OrderRoots`, so `OrderRoots` has two `<summary>` blocks and `OrderReachable` has none. Move it back to `OrderReachable`.

### 7. Note for the spec session (already question 25): no `cld` in handlers

Tern code never sets decimal mode, but an asm block in main can. A handler that runs during such a block then does its `adc`/`sbc` in decimal mode. An `asm` block that sets `sed` can usually wrap itself in `sei`/`cli`, so this is fine as a documented rule. It should be written down in spec 6.3 when question 25 is settled.

## Checked and correct

- Jump-table bounds: after `sec` / `sbc #low`, values below `low` wrap to at least `256 - low`, which is at least `span`, so `cmp #span` / `bcs` catches both sides. When `span` is 256, no check is emitted, which is correct.
- Compare chain: in source order, the inverted last test falls through to the last arm's body, and ranges at the ends of the byte use one compare. `i8` ranges across zero are correct (probe over all 256 values).
- Handler save/restore: A whenever X or Y is saved; restored in the reverse order; `return` goes to the restore code; calls (including `jsr` in asm and inline copies) count as changing all registers (`AsmEffects`: `jsr` writes A, X, Y).
- `FrameOffsets`: handlers come after main's whole tree in `OrderRoots`, and their callees follow them, in RAM and in zero page. A handler's own temporaries are in its own frame (`h._t0`).
- Inline copies: asm local labels are unique per copy (`spin.l1`, `spin.l3`); `return` jumps to the copy's end; the caller's temporaries survive.
- `noinit`: placed after the zeroed range; skipped in zero-page startup; errors for an initial value, a fixed address, `data` and locals.
- M5 follow-up: `private` lookup (Tern code and asm), `addr()` of fields, `linear` 16-bit arrays (`asl` / `tax` shape, interleaved initial values, at most 128 elements).
- Emulator: `Irq()` respects I, pushes P with B clear and sets I; `Nmi()` ignores I. The test CPU now starts with I set.
