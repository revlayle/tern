### 1. Must fix: sprite registers are written during the last line the previous sprite is still drawn

`sprites.tern:191-199` (`emit`) sets `d_line = d_y[e-8] + 21`, and `raster()` writes entry `e` once the raster reaches that line. On the VIC-II, a sprite with y register `Y` is compared in cycles 55-56 of line `Y`, and its rows are drawn on lines `Y+1` to `Y+21`. Line `Y+21` still shows the last row. A write to `$D027+k` (color), `$D000+2k` (x), `$D010`, `$D01C` or `$D01D` early in that line changes how the old sprite's last row is drawn.

`FakeVic` hides this. It draws a sprite on lines `Y` to `Y+20` (`FakeVic.cs:109-110`), one line earlier than the real chip, and it reads the registers at the start of each line. `SpriteTests.Expected` and `GraphicsExampleTests` use the same `Y..Y+20` window.

Failing case: I ran the example under `FakeVic` (with `stealCycles`) for 160 frames, in a temporary worktree that has since been removed. For each color or x write to hardware sprite `k`, I checked whether it landed on line `oldY + 21` before the beam reached the old sprite (cycle about `13 + x/8`). 12 of 6720 writes did. All were color writes for sprites on the right half of the screen. Examples: line 71, slot 1, color written at cycle 50, old sprite y 50, x 293; line 134, slot 1, cycle 45, y 113, x 283. They come from the paths where `put` runs without waiting: the line is already reached in the `while` loop, or the line arrives between the write to `$D012` and the re-check. The ball's last row (`$00, $7E, $00`) is not empty, so the bottom 6 pixels of a ball then show for one line in the next sprite's color. This is rare and small, but the multiplexer is a library, and the roadmap's done-when says "without visible glitches".

Fix: `d_line = y + 22`. `GAP` = 30 still leaves 8 lines for the writes, so the 5-sprite group test should hold, but check it. Also make `FakeVic` draw lines `Y+1..Y+21` and update `Expected` and the example test to match, so the tests check real hardware timing. Optionally, `FakeVic` could flag a register write on a line where that sprite is still drawn, before the beam reaches its x; that is the check above.

### 2. Suggestion: during a diagonal's alignment phase, prepare the diagonal screen, not the straight one

`scroll.tern:227-247`: when the two axes are not equally far from their coarse steps, `move` changes `mx` or `my` to 0, and then uses this reduced direction as the key for preparing the hidden screen. While they align, the moving axis cannot reach its step (it stops when its distance equals the other's), so the next coarse step is always the diagonal one. The straight preparation is thrown away when the key changes to the diagonal one. The diagonal then has only the remaining pixels, at 3 steps per call, for 17 steps. Example: `move(1, 1)` from `fine_x = 3`, `fine_y = 0` moves y alone for 3 frames, preparing `(0, 1)`. It then switches to `(1, 1)` with 4 pixels left, which is at most 12 steps, so the camera holds at the step. Setting `key_x`/`key_y` from the requested `dx`/`dy` would prepare the right screen all along, and that stall would go away. The "up to 6 frames" note in the header could then be shorter.

### 3. Suggestion: unreachable branches in the coarse step of `move`

`scroll.tern:284, 287, 291, 294`: the `else { fine_x += 1 }` branches (and the same for `-= 1` and `fine_y`) run only when an axis is moving but not crossing during a coarse step. The alignment code rules that out: either one axis is set to 0, or both reach their step together. If one did run, it would be wrong, because `cell_x`/`cell_y` would change without the fine scroll wrapping. Remove them, so that each moving axis is just `cell += 1; fine = 0`, or `cell -= 1; fine = 7`.

### 4. Suggestion: `COLORS` does not race the beam reliably, and that is not tested

`finish()` redraws the color RAM with `mem.copy`, about 480 cycles per row (status: 12,000 for 1000 bytes). Without sprites, the CPU gets about 464 cycles per character row (8 lines minus a bad line), so the copy falls behind the beam by about 16 cycles a row. It starts about 3,200 cycles ahead (line 51), minus the handler and `wait_frame`. With the multiplexer's interrupts (about 5,000 cycles a frame) and sprite DMA, it is overtaken in the lower half. Those rows then show new characters with old colors for one frame at every coarse step. This is an estimate; no test checks color RAM writes against the bad lines. Spec 10.1 asks for an asm shift that races the beam, and question 46(c) asks the spec session to accept a redraw. Until that is decided, either test it under `FakeVic` (each color row written before its bad line), or say in the module header that `COLORS` should not be combined with the multiplexer. The example does not use `COLORS`.

### 5. Suggestion: comments disagree on group size

The `sprites.tern` header (lines 34-35) says a group that starts on one line "is drawn whole up to four sprites; from the fifth, the registers are written late". The `GAP` comment (line 52) says "about 4 sprites' worth". `docs/status.md` and question 47 say groups of up to 5 are drawn whole, and `Rows_of_sprites_that_start_together_are_drawn_whole` tests 5. Make them agree, after the change for finding 1.

### For the spec session (not blocking)

Questions 46-49 in `docs/status.md` record the API as built and how it differs from the "Planned for M11" text in spec 10.1: parallel arrays instead of a struct table, the `SCREEN`/`SCREEN2`/`SCREEN_A`/`SCREEN_B`/`COLORS` parameters, a color redraw instead of a shift, the sprite limits, the `put` helper as an `interrupt fn`, and dead `if FLICKER` branches still linking their callees. The choices are reasonable and marked provisional. Spec 10.1 should be updated from them.
