## Findings

### 1. Command-line errors have no suggestion in `--json` (suggestion)

`Cli.Commands.cs:193` makes every usage error as `"{problem}. Run 'tern --help' for the options"`. "Run" is not in `Diagnostic.FixVerbs`, and the fixes inside the problems follow a colon ("No target given: write --target c64, ..."), so `Diagnostic.Split` finds no fix:

```
tern --target zx --json ok.tern      "suggestion": null   (Unknown target 'zx': write --target c64, ...)
tern --json --max-errors abc ...     "suggestion": null
tern run --set zz --json ...         "suggestion": null
tern --json --bogus ok.tern          "suggestion": null
tern run --dump out:0 --json ...     "suggestion": null   ("the byte count must be at least 1", RunReport.cs:20: no fix at all)
```

The status's behavior changes say "a tool's error (path, option, run) has its suggestion in `--json`". That holds for paths and run errors, not for options. `CliTests.cs:240` accepts a null suggestion (it rebuilds the text either way), so no test catches it. Fix: write each problem's fix as its own sentence with a fix verb ("Unknown target 'zx'. Use --target c64, ..."), and let the test require a suggestion. With question 177 (a message's fix as its own part) this may become a field instead. Also, the `--dump` error names the source file (`"file": "ok.tern"`) where the other command-line errors give `""`. Tools 7 asked for "no file".

### 2. The module parameter's fallback message has two fixes, and no test (suggestion)

`Checker.Declarations.cs:259` appends a second fix to the whole message of the error it caught. For `import m(n = zz)`:

> 'zz' is not declared. Check the spelling, or declare it. A parameter value uses literals and the main file's constants that do not depend on imported modules. Write the value as a number

`--json` puts all of it after "Check the spelling" into the suggestion, which tells the user both to declare `zz` and to write a number. This was on `main` already, but it is the message semantics 17's commit reworked, and it is the "message text as data" pattern R6 removes elsewhere (a caught message's text reused as the start of a new one). No test reaches it: `ModuleParameterTests` tests only the `NotDeclared` branch above it. Fix: make the message from the error's reason (`NotDeclared` gives the name), as the branch above does, with one fix. R8's list of unreached messages (tests 4) would also find it.

### 3. Platform names and facts outside the descriptions (suggestion)

The done-when is met for what a build does: a new platform is a `Platform` with its `OutputFormat` and `Machine`. Three texts still name platforms, so a new platform needs edits outside its description:

- `MemoryLayout.cs:76`: "'cartridge' is not supported yet for the c64: cartridge images are built only for the NES so far". The NES is named in shared code, and the message uses `platform.Name` ("the c64"), where the next message and `PlatformDataTests` use `Title` ("The Apple II has no cartridges"). `MemoryLayout.cs:110` has the same `Name` for `Title`.
- `Cli.cs:162-165`: the help's run-model paragraph names the C64, the Atari, the Apple II and the NES one by one. A fifth machine is left out of the help until someone edits it. Each `Machine` could give its own paragraph (as `StandIns` already does), and the help could list `Platform.All`.
- `ProDosSystem.cs:44` finds the `io` library module by name (`m.Name == "io"`; syntax 6 named this as `withIo`). It now sits inside the Apple II's own output, so the reach is smaller. A platform library property (the module whose prefix parameters the startup code fills) would remove the name.

### 4. The tests' run loop is a second copy of `tern run`'s (suggestion)

Tests 13 asked for `Run` and `Runner` to "share one run model". They now share the machine (loading, bus, chips, stand-ins, screen), which is the main part. The loop is still written twice (`Run.cs:57-90`, `Runner.cs:97-140`): the IRQ timing, the stand-in's return as `rts`, and the index check before each step. The copies already differ. `Run` ignores the result of `_machine.AfterStep(Cpu)` (`Run.cs:87`), so an NES run's NMIs are not counted in `Run.Interrupts`, while `Runner` counts them. `Run` also never asks `RunsBrk`. Today no test reads `Interrupts` on the NES. Fix: one step loop in `Tools` with hooks for traps and the plain-build comparison, or at least add the NMI to `Interrupts`. This can wait for after the release, like tools 18's other parts.

### 5. A fourth copy of the CLI helper (suggestion)

`TargetTests.cs:16-21` keeps its own `Tern(params string[])`, which differs from `Command.Tern` only in trimming standard error. Tests 7's rest asked for one. Use `Command.Tern` and trim where the test compares.

### 6. `Diagnostic`'s doc comment is on `Severity` (suggestion)

`Diagnostics.cs:6-11`: the `<summary>` written for `Diagnostic` now stands above `Severity`'s own `<summary>`. So the enum has two summaries and the record none (`b5a8785` put the enum between them). Move the first summary down to the record.

### 7. The bool-to-number fix leaves out `as u8` (suggestion, not R6's)

Found while running semantics 12's programs. `x = b` (a `u8` from a `bool`) says "Use 'if' to choose a number, as in 'if b { x = 1 }'" (`Checker.TypeRules.cs`, the `found bool` message). Spec 3.5 allows `bool as u8` (0 or 1, `lda #0` / `rol` from a flag), which is shorter and is what the user most likely wants. The example also always says `b` and `x`, whatever the names are. Fix: "Convert with 'b as u8' (0 or 1), or use 'if' to choose another number", with the names from the expression. This was on `main` already, and R8's message work is the natural place for it.
