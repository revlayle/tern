## How the numbers are taken

- **Cycles** run from the first instruction of the program's `main` to its final `rts`. Startup is not counted:
  for Tern, cc65 and llvm-mos the startup code runs first and timing starts when `main` is entered; the assembly has none.
  The numbers in `baseline.txt` are different: they cover the whole Tern program, startup included.
- **Bytes** are the program's code and data, and for Prog8, cc65 and llvm-mos the library routines it uses. Left out: the BASIC
  line and startup code (Tern, from the `main` label on); the BASIC line, entry code and the C64 startup/exit block
  (Prog8); the startup modules (cc65); the BASIC header, startup modules, `exit` and `__memset` (llvm-mos); variables in BSS (all).
- Variables start at zero in every version. Tern, the assembly, cc65 and llvm-mos do the clearing outside the measured part
  (Tern's startup, zeroed memory, cc65's `zerobss`, llvm-mos's `__zero_bss`). Prog8 clears its BSS and initialises variables at the start of
  `main`, so its bytes and cycles include that.
- **Prog8**: 12.0-SNAPSHOT, `%zeropage basicsafe`, `%option no_sysinit`, default optimisation.
- **cc65**: `cl65 -t none -Oirs -Cl` (inlining, register variables, static locals).
- **llvm-mos**: `mos-c64-clang -Os -fno-lto` (the llvm-mos SDK; without link-time optimisation, which would remove the result variables that only the test reads). The same C sources as cc65.
  Its startup code runs in the emulator with the KERNAL's `CHROUT` stubbed out as an `rts`. It keeps small globals in zero page.
- **Assembly**: written for the task, in the style of an experienced programmer: registers and zero page for
  values, constants where the task fixes them (the copy sizes), no generic library routines. The `interp` dispatch
  does not range-check the opcode, where Tern's `match` sends other values to the `_` arm.
- **Data layout**: Tern, the assembly and Prog8 keep `enemies` as one table per field; the C versions use an array of
  structs (natural C), so each access multiplies the index by 5. Their large `enemies` cycle counts are that choice, not
  only the C compilers' code generation.
